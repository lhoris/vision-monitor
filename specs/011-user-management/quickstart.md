# Quickstart: 사용자 관리

## 목적

사용자관리 기능 구현 후 핵심 동작을 검증하는 절차다. MVP에서는 tester 계정 기반 mock 흐름을 기준으로 확인한다.

## 사전 조건

- frontend 의존성이 설치되어 있어야 한다.
- 사용자관리 구현은 `/admin/users` route에 연결되어 있어야 한다.
- `tester / tester123`은 관리자 mock 계정이다.
- `tester1 / tester123`은 비관리자 mock 계정이다.

## 실행

```powershell
cd frontend
npm test
npm run build
npm run dev
```

## 검증 시나리오

### 1. 관리자 mock 계정 접근

1. `/login`에서 `tester / tester123`으로 로그인한다.
2. 사이드바를 연다.
3. `사용자 관리` 메뉴를 선택한다.

**기대 결과**: `/admin/users` 화면에 사용자관리 그리드가 표시된다.

### 2. 비관리자 mock 계정 접근 제한

1. 로그아웃한다.
2. `/login`에서 `tester1 / tester123`으로 로그인한다.
3. 사이드바를 연다.
4. 직접 `/admin/users`로 접근한다.

**기대 결과**: 관리자 메뉴가 표시되지 않고 직접 접근 시 `/live`로 이동한다.

### 3. 사용자 검색과 필터

1. `tester`로 로그인한 상태에서 `/admin/users`를 연다.
2. 사용자 ID 또는 이름을 검색한다.
3. 역할, 계정 상태, 재직 상태 필터를 적용한다.
4. 필터를 초기화한다.

**기대 결과**: 조건에 맞는 사용자만 표시되고 초기화 시 전체 목록으로 돌아간다.

### 4. 신규 사용자 등록 validation

1. 사용자 추가를 선택한다.
2. 필수값을 비운 채 저장한다.
3. 기존 사용자 ID와 같은 값을 입력하고 저장한다.
4. 올바른 값과 역할을 입력하고 저장한다.

**기대 결과**: 필수값/중복 오류가 표시되고, 유효한 입력은 그리드와 상세 정보에 반영된다.

### 5. 역할 수정과 영향 안내

1. 기존 사용자를 선택한다.
2. 역할을 변경한다.

**기대 결과**: 메뉴 접근, 권한 정책, 영상그리드 개인화 가능 범위에 영향이 있을 수 있다는 안내가 표시된다.

### 6. 비활성화와 퇴사 처리

1. 활성 사용자를 선택한다.
2. 비활성화를 실행한다.
3. 다른 사용자를 선택해 퇴사 처리를 실행한다.
4. 개인화 설정 보유 사용자인 경우 유지/초기화 선택을 확인한다.

**기대 결과**: 계정 상태와 재직 상태가 명확히 구분되어 표시되고 개인화 처리 선택지가 표시된다.

### 7. 위험 변경 방지

1. 현재 로그인한 `tester` 계정을 선택한다.
2. 자기 계정 비활성화 또는 삭제 요청을 시도한다.
3. 마지막 관리자만 남는 fixture에서 관리자 제거를 시도한다.

**기대 결과**: 자기 계정 잠금과 마지막 관리자 제거는 경고되거나 차단된다.

## 회귀 확인

- `tester`는 관리자 메뉴를 계속 볼 수 있어야 한다.
- `tester1`은 관리자 메뉴를 볼 수 없어야 한다.
- `/live`, `/playback`, `/events` route는 기존처럼 동작해야 한다.
- theme1, theme2, theme3에서 그리드 텍스트와 상태 배지가 읽을 수 있어야 한다.
