# 기능 명세서: 사용자 관리

**기능 브랜치**: `011-user-management`

**작성일**: 2026-08-17

**상태**: 초안

**변경 추적**: 문서 변경 이력은 Git 커밋 이력을 기준으로 한다.

**입력**: Spec Kit 작업 디렉터리를 사용자관리로 변경하고, 사용자관리 화면을 업무시스템에 필요한 수준으로 보강한다. 화면은 그리드 형태를 기본으로 하며 신규 사용자 등록, 삭제, disable 또는 퇴사 처리, 권한 및 개인화 기능과의 연동 기반 데이터까지 포함한다.

> 이 문서는 한국어로 작성한다. 기술 용어, API 이름, 파일 경로, 코드 식별자는 원문 또는 영문 표기를 유지할 수 있다.
> 기능 명세서는 "무엇을 제공해야 하는가"를 정의한다. 구현 방식, 컴포넌트 구조, DTO/API 세부사항, 파일 경로는 plan.md 또는 contracts/에서 다룬다.

> **기능 개요 - Agent 요약**
>
> 사용자 관리는 관리자 권한 사용자가 Vision Monitor를 사용하는 계정의 생명주기를 관리하는 기본 관리자 기능이다. 관리자는 그리드 형태의 목록에서 사용자를 조회하고, 신규 등록, 기본 정보 수정, 역할 배정, 계정 잠금/해제, 비활성화, 퇴사 처리, 삭제 요청 같은 업무시스템의 일반적인 계정 관리 작업을 수행할 수 있어야 한다. 사용자 데이터는 권한 정책, 메뉴 접근, 라이브 대시보드 영상그리드 개인화 같은 후속 기능의 기준 데이터가 되므로 사용자 상태와 역할, 소속, 사용 가능 여부가 명확해야 한다. MVP에서는 mock 데이터 기준으로 사용자관리 화면과 상태 흐름을 정의하고, 실제 인증 저장소/DB/SSO/MFA 연동은 후속 범위로 둔다.

## 2. 기능 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 관리자 권한 사용자는 왼쪽 사이드바의 관리자 메뉴에서 사용자 관리 화면에 진입할 수 있어야 한다.
- **FR-002**: 관리자 권한이 없는 사용자는 사용자 관리 메뉴와 화면에 접근할 수 없어야 한다.
- **FR-003**: 시스템은 사용자 목록을 그리드 형태로 표시해야 한다.
- **FR-004**: 그리드는 사용자 ID, 이름, 표시명, 부서/소속, 직책, 이메일, 연락처, 역할, 계정 상태, 재직 상태, 마지막 접속 시각, 최근 수정 정보를 표시할 수 있어야 한다.
- **FR-005**: 사용자는 사용자 ID, 이름, 부서/소속, 역할, 계정 상태, 재직 상태 조건으로 목록을 검색하거나 필터링할 수 있어야 한다.
- **FR-006**: 사용자는 그리드 정렬, 페이지 이동 또는 표시 건수 조정으로 많은 사용자 목록을 탐색할 수 있어야 한다.
- **FR-007**: 관리자는 그리드에서 사용자를 선택해 상세 정보를 확인할 수 있어야 한다.
- **FR-008**: 관리자는 신규 사용자를 등록할 수 있어야 한다.
- **FR-009**: 신규 사용자 등록 시 시스템은 사용자 ID, 이름 또는 표시명, 역할, 계정 상태, 재직 상태를 필수 정보로 요구해야 한다.
- **FR-010**: 시스템은 중복 사용자 ID, 필수값 누락, 잘못된 이메일 형식처럼 저장할 수 없는 입력을 저장 전에 표시해야 한다.
- **FR-011**: 관리자는 기존 사용자의 기본 정보, 부서/소속, 연락처, 역할, 계정 상태, 재직 상태를 수정할 수 있어야 한다.
- **FR-012**: 관리자는 사용자에게 하나 이상의 역할을 배정할 수 있어야 한다.
- **FR-013**: 시스템은 사용자의 역할 변경이 메뉴 접근, 권한 정책, 영상그리드 개인화 가능 범위에 영향을 줄 수 있음을 표시해야 한다.
- **FR-014**: 관리자는 사용자 계정을 활성, 잠금, 비활성, 퇴사 처리 상태 중 하나로 관리할 수 있어야 한다.
- **FR-015**: 비활성 또는 퇴사 처리된 사용자는 로그인 가능 사용자로 오해되지 않도록 명확히 구분되어야 한다.
- **FR-016**: 관리자는 사용자 계정을 삭제 요청할 수 있어야 한다.
- **FR-017**: 시스템은 사용자 삭제보다 비활성 또는 퇴사 처리를 우선 선택할 수 있게 안내해야 한다.
- **FR-018**: 시스템은 삭제 요청 전 해당 사용자의 권한, 개인화 설정, 이력 참조 가능성에 대한 영향 안내를 표시해야 한다.
- **FR-019**: 시스템은 자기 자신의 관리자 권한 제거, 자기 계정 비활성화, 자기 계정 삭제처럼 운영자 자신을 잠글 수 있는 위험 동작을 경고하거나 차단해야 한다.
- **FR-020**: 시스템은 모든 관리자 계정이 사라지는 변경을 경고하거나 차단해야 한다.
- **FR-021**: 관리자는 사용자의 개인화 설정 보유 여부를 확인할 수 있어야 한다.
- **FR-022**: 관리자는 사용자의 개인화 설정을 유지할지 초기화할지 선택할 수 있어야 한다.
- **FR-023**: 시스템은 사용자 목록 없음, 필터 결과 없음, 저장 실패, 권한 없음 상태를 서로 구분해 표시해야 한다.
- **FR-024**: 시스템은 사용자 추가/수정/삭제/비활성화 요청의 성공, 실패, 처리 중 상태를 구분해 표시해야 한다.
- **FR-025**: 시스템은 사용자 변경 후 그리드 목록과 상세 정보가 같은 상태를 보여주도록 갱신해야 한다.

## 3. 제외 범위 *(필수)*

- 실제 인증 저장소, DB, Spring Boot API 구현은 MVP 범위에서 제외한다.
- 실제 비밀번호 변경, 비밀번호 초기화, MFA, SSO, 사번/인사 시스템 연동은 제외한다.
- 상세 감사 로그, 결재/승인 워크플로우, 계정 잠금 정책 자동화는 제외한다.
- 사용자별 세부 권한 정책 편집은 013 권한 정책 관리 범위로 분리한다.
- 역할 자체의 생성/수정/비활성화는 012 역할 관리 범위로 분리한다.
- 메뉴별 접근 권한 상세 관리는 별도 메뉴 접근 권한 관리 범위로 분리한다.
- 실제 개인정보 암호화, 마스킹, 보존 기간 정책 구현은 후속 보안/운영 정책 범위로 둔다.

## 4. UI/UX 요구사항

- **UX-001**: 사용자 관리의 기본 화면은 그리드 목록을 중심으로 구성되어야 한다.
- **UX-002**: 그리드 행 선택, 추가, 수정, 비활성화, 퇴사 처리, 삭제 요청 동작은 서로 구분되어야 한다.
- **UX-003**: 상태 배지는 색상만으로 의미를 전달하지 않고 상태 텍스트를 함께 표시해야 한다.
- **UX-004**: 활성, 잠금, 비활성, 퇴사 상태는 목록과 상세 영역에서 일관되게 표시되어야 한다.
- **UX-005**: 사용자 추가/수정 입력은 기본 정보, 조직 정보, 권한 정보, 계정 상태, 개인화 설정 영역으로 구분되어야 한다.
- **UX-006**: 필수 입력 오류와 중복 오류는 해당 입력 항목 근처에서 확인할 수 있어야 한다.
- **UX-007**: 삭제, 퇴사 처리, 자기 계정 변경 같은 위험 동작은 확인 절차와 영향 안내가 있어야 한다.
- **UX-008**: 많은 사용자를 다루는 화면이므로 검색, 필터, 정렬, 페이지 이동이 빠르게 이해되어야 한다.
- **UX-009**: 그리드 안의 긴 이름, 긴 이메일, 긴 부서명이 레이아웃을 깨뜨리지 않아야 한다.
- **UX-010**: theme1, theme2, theme3에서 그리드 텍스트, 상태 배지, 입력값, 오류 메시지, 확인 대화상자가 읽을 수 있어야 한다.

## 5. 필요한 정보

- 사용자 ID, 이름, 표시명, 이메일, 연락처
- 부서/소속, 직책, 현장 또는 담당 공정
- 역할 목록과 대표 역할
- 계정 상태: 활성, 잠금, 비활성
- 재직 상태: 재직, 휴직, 퇴사
- 마지막 접속 시각, 생성자, 생성 시각, 최근 수정자, 최근 수정 시각
- 개인화 설정 보유 여부와 초기화 가능 여부
- 사용자 변경이 권한 정책, 메뉴 접근, 영상그리드 개인화에 미치는 영향
- 관리자 권한 여부와 자기 계정 여부

## 6. 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 사용자 그리드 조회와 검색 (우선순위: P1)

관리자는 사용자 관리 화면에서 전체 사용자를 그리드로 확인하고 필요한 사용자를 검색한다.

**관련 기능 요구사항**: FR-001, FR-002, FR-003, FR-004, FR-005, FR-006, FR-023

**이 우선순위의 이유**: 사용자 관리는 계정 현황을 빠르게 찾고 상태를 파악하는 작업에서 시작한다.

**독립 테스트**: 관리자 권한으로 사용자 관리 화면에 진입해 그리드 목록, 검색, 필터, 정렬, 빈 상태를 확인한다.

**허용 시나리오**:

1. **Given** 관리자 권한 사용자가 로그인되어 있다, **When** 사용자 관리 메뉴를 선택한다, **Then** 사용자 그리드가 표시된다.
2. **Given** 사용자 그리드가 표시되어 있다, **When** 사용자가 이름 또는 사용자 ID로 검색한다, **Then** 조건에 맞는 사용자만 표시된다.
3. **Given** 역할과 계정 상태 필터가 적용되어 있다, **When** 관리자가 필터를 초기화한다, **Then** 전체 사용자 목록으로 돌아간다.
4. **Given** 검색 결과가 없다, **When** 그리드를 확인한다, **Then** 필터 결과 없음 상태가 표시된다.
5. **Given** 비관리자 사용자가 로그인되어 있다, **When** 사이드바를 확인한다, **Then** 사용자 관리 메뉴가 표시되지 않는다.

---

### 사용자 스토리 2 - 신규 사용자 등록 (우선순위: P1)

관리자는 신규 사용자를 등록하고 기본 역할과 계정 상태를 지정한다.

**관련 기능 요구사항**: FR-008, FR-009, FR-010, FR-012, FR-013, FR-024, FR-025

**이 우선순위의 이유**: 신규 사용자 등록은 사용자관리의 핵심 업무이며 권한과 개인화 기능의 출발점이다.

**독립 테스트**: 신규 사용자 등록 화면에서 필수값, 중복 사용자 ID, 역할 배정, 저장 성공/실패 상태를 확인한다.

**허용 시나리오**:

1. **Given** 사용자 관리 화면이 표시되어 있다, **When** 관리자가 사용자 추가를 선택한다, **Then** 신규 사용자 입력 화면이 표시된다.
2. **Given** 필수 입력값이 비어 있다, **When** 관리자가 저장을 시도한다, **Then** 누락된 입력값 오류가 표시된다.
3. **Given** 이미 존재하는 사용자 ID가 입력되어 있다, **When** 관리자가 저장을 시도한다, **Then** 중복 사용자 ID 오류가 표시된다.
4. **Given** 입력값이 유효하고 역할이 선택되어 있다, **When** 관리자가 저장한다, **Then** 신규 사용자가 그리드에 표시되고 상세 정보가 갱신된다.

---

### 사용자 스토리 3 - 사용자 정보와 역할 수정 (우선순위: P1)

관리자는 기존 사용자의 기본 정보와 역할을 수정하고 권한 영향 범위를 확인한다.

**관련 기능 요구사항**: FR-007, FR-011, FR-012, FR-013, FR-021, FR-024, FR-025

**이 우선순위의 이유**: 역할과 사용자 정보 변경은 권한 정책, 메뉴 접근, 개인화 기능에 직접 영향을 준다.

**독립 테스트**: 사용자 선택, 상세 확인, 역할 변경, 개인화 보유 여부 표시, 저장 결과를 확인한다.

**허용 시나리오**:

1. **Given** 사용자 그리드가 표시되어 있다, **When** 관리자가 특정 사용자를 선택한다, **Then** 사용자 상세 정보가 표시된다.
2. **Given** 사용자 상세 정보가 표시되어 있다, **When** 관리자가 역할을 변경한다, **Then** 권한과 개인화 영향 안내가 표시된다.
3. **Given** 수정 정보가 유효하다, **When** 관리자가 저장한다, **Then** 그리드와 상세 정보가 변경된 값으로 갱신된다.

---

### 사용자 스토리 4 - 비활성화와 퇴사 처리 (우선순위: P2)

관리자는 사용하지 않는 계정을 비활성화하거나 퇴사 처리한다.

**관련 기능 요구사항**: FR-014, FR-015, FR-017, FR-019, FR-020, FR-021, FR-022, FR-024

**이 우선순위의 이유**: 접근 권한 회수는 보안과 운영 안정성에 중요하며 삭제보다 더 자주 발생하는 업무다.

**독립 테스트**: 활성 계정 비활성화, 퇴사 처리, 자기 계정 위험 경고, 개인화 설정 유지/초기화 선택을 확인한다.

**허용 시나리오**:

1. **Given** 활성 사용자가 선택되어 있다, **When** 관리자가 비활성화를 실행한다, **Then** 계정 상태가 비활성으로 표시된다.
2. **Given** 재직 사용자가 선택되어 있다, **When** 관리자가 퇴사 처리를 실행한다, **Then** 재직 상태가 퇴사로 표시되고 로그인 가능 계정으로 오해되지 않게 표시된다.
3. **Given** 사용자에게 개인화 설정이 있다, **When** 관리자가 퇴사 처리를 실행한다, **Then** 개인화 설정 유지 또는 초기화 선택지가 표시된다.
4. **Given** 관리자가 자기 계정을 비활성화하려 한다, **When** 저장을 시도한다, **Then** 위험 변경 경고 또는 차단이 표시된다.

---

### 사용자 스토리 5 - 삭제 요청과 위험 변경 방지 (우선순위: P3)

관리자는 사용자 삭제가 필요한 경우 영향 범위를 확인하고 삭제 요청을 수행한다.

**관련 기능 요구사항**: FR-016, FR-017, FR-018, FR-019, FR-020, FR-024

**이 우선순위의 이유**: 삭제는 이력과 권한/개인화 참조를 끊을 수 있어 비활성화보다 신중해야 한다.

**독립 테스트**: 삭제 요청 전 영향 안내, 비활성화 우선 안내, 모든 관리자 제거 방지, 처리 상태 표시를 확인한다.

**허용 시나리오**:

1. **Given** 사용자가 선택되어 있다, **When** 관리자가 삭제 요청을 선택한다, **Then** 비활성화 우선 안내와 삭제 영향 범위가 표시된다.
2. **Given** 삭제 대상이 마지막 관리자 계정이다, **When** 관리자가 삭제를 확정하려 한다, **Then** 변경이 경고되거나 차단된다.
3. **Given** 삭제 요청이 실패했다, **When** 결과가 표시된다, **Then** 실패 메시지가 표시되고 기존 사용자 정보는 유지된다.

### 엣지 케이스

- 모든 관리자 계정이 비활성화되거나 삭제되는 상황은 경고 또는 차단되어야 한다.
- 자기 자신의 계정 상태, 역할, 삭제 요청은 일반 사용자 변경보다 더 강한 확인 절차가 필요하다.
- 사용자명이 길거나 이메일이 길어도 그리드와 상세 화면이 깨지지 않아야 한다.
- 비활성 또는 퇴사 계정은 로그인 가능한 활성 계정으로 오해되지 않아야 한다.
- 역할이 없는 사용자는 기본 업무 화면 접근 권한이 없을 수 있음을 표시해야 한다.
- 개인화 설정이 있는 사용자를 삭제하거나 퇴사 처리할 때 설정 처리 방식을 명확히 해야 한다.
- 저장 실패가 발생해도 입력 중인 사용자 정보는 사라지지 않아야 한다.
- 비관리자가 직접 사용자관리 route에 접근하면 화면 내용을 볼 수 없어야 한다.

## 7. 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 관리자는 로그인 후 2번 이하의 조작으로 사용자 관리 화면에 진입할 수 있다.
- **SC-002**: 관리자는 3초 이내에 사용자 그리드에서 활성, 비활성, 퇴사 계정 수와 주요 상태를 파악할 수 있다.
- **SC-003**: 관리자는 3개 이하의 검색/필터 조작으로 특정 사용자나 특정 역할 사용자를 찾을 수 있다.
- **SC-004**: 필수값 누락, 중복 사용자 ID, 잘못된 이메일 형식은 저장 전에 표시된다.
- **SC-005**: 신규 사용자 등록 또는 사용자 정보 수정 후 그리드와 상세 정보가 같은 상태를 보여준다.
- **SC-006**: 자기 계정 잠금, 마지막 관리자 제거, 삭제 요청 같은 위험 변경은 확인 없이 저장되지 않는다.
- **SC-007**: 비관리자는 사용자 관리 메뉴와 화면 내용을 볼 수 없다.
- **SC-008**: theme1, theme2, theme3에서 그리드 텍스트, 상태 배지, 입력 오류, 위험 동작 확인 메시지가 읽을 수 있게 표시된다.

## 8. 가정 및 미정 사항

### 가정

- MVP는 mock 사용자 목록과 mock 저장 흐름으로 진행한다.
- `tester / tester123`은 관리자 사용자로, `tester1 / tester123`은 비관리자 사용자로 검증한다.
- 사용자 역할은 012 역할 관리의 역할 정의를 참조한다.
- 사용자 권한과 메뉴 접근 결과는 013 권한 정책 관리 및 후속 메뉴 접근 권한 관리 기능과 연동된다.
- 라이브 대시보드 영상그리드 개인화 설정은 사용자 ID를 기준으로 연결된다.
- 삭제는 운영 리스크가 크므로 기본 안내는 비활성화 또는 퇴사 처리를 우선한다.

### 미정 사항

- 실제 사용자 필드의 최종 필수 항목과 개인정보 마스킹 정책은 운영 보안 정책 확정 후 조정한다.
- 비밀번호 정책, 계정 잠금 자동화, SSO/MFA 연동은 후속 인증/보안 명세에서 정한다.
- 삭제가 물리 삭제인지 논리 삭제인지는 backend 및 감사 정책 확정 후 정한다.
