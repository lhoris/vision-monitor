# 기능 명세서: 사용자 관리

**기능 브랜치**: `011-user-management`

**작성일**: 2026-08-17

**상태**: 초안

**변경 추적**: 문서 변경 이력은 Git 커밋 이력을 기준으로 한다.

**입력**: 왼쪽 사이드바 관리자 메뉴 순서에 따라 "사용자 관리" 기능명세서 작성

> **기능 개요 - Agent 요약**
>
> 사용자 관리는 관리자 권한 사용자가 시스템에 접근하는 사용자 계정을 조회하고 기본 상태를 관리하는 기능이다. 관리자는 사용자 목록, 계정 상태, 역할, 마지막 접속 정보를 확인하고 필요 시 계정을 추가, 수정, 비활성화할 수 있어야 한다. MVP에서는 mock 계정 기준의 관리 화면과 권한 경계를 정의하고, 실제 인증 저장소와 비밀번호 정책 연동은 후속 범위로 둔다.

## 2. 기능 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 관리자 권한 사용자는 사용자 관리 화면에 진입할 수 있어야 한다.
- **FR-002**: 관리자 권한이 없는 사용자는 해당 메뉴와 화면에 접근할 수 없어야 한다.
- **FR-003**: 시스템은 사용자 목록을 표시해야 한다.
- **FR-004**: 시스템은 사용자 ID, 이름, 역할, 계정 상태, 마지막 접속 정보를 표시해야 한다.
- **FR-005**: 사용자는 사용자명, 역할, 계정 상태 조건으로 목록을 필터링할 수 있어야 한다.
- **FR-006**: 관리자는 사용자 상세 정보를 확인할 수 있어야 한다.
- **FR-007**: 관리자는 신규 사용자를 추가할 수 있어야 한다.
- **FR-008**: 관리자는 기존 사용자 정보를 수정할 수 있어야 한다.
- **FR-009**: 관리자는 사용자 계정을 비활성화할 수 있어야 한다.
- **FR-010**: 시스템은 자기 자신의 관리자 권한을 실수로 제거하거나 비활성화하는 위험을 경고해야 한다.
- **FR-011**: 시스템은 필수 사용자 정보 누락과 중복 사용자 ID를 저장 전에 표시해야 한다.
- **FR-012**: 시스템은 사용자 삭제보다 비활성화를 우선 제공해야 한다.

## 3. 제외 범위 *(필수)*

- 실제 인증 저장소 연동은 제외한다.
- 비밀번호 초기화, MFA, SSO 연동은 제외한다.
- 상세 감사 로그와 계정 잠금 정책 구현은 제외한다.
- 조직도/인사 시스템 연동은 제외한다.

## 4. UI/UX 요구사항

- **UX-001**: 사용자 목록은 계정 상태와 역할을 빠르게 구분할 수 있어야 한다.
- **UX-002**: 추가/수정 화면은 필수 정보와 역할 선택을 명확히 구분해야 한다.
- **UX-003**: 위험 동작은 확인 절차와 영향 안내가 있어야 한다.
- **UX-004**: 비활성 계정은 활성 계정과 명확히 구분되어야 한다.
- **UX-005**: theme1, theme2, theme3에서 사용자명, 역할, 상태가 읽을 수 있어야 한다.

## 5. 필요한 정보

- 사용자 ID, 이름, 역할, 계정 상태
- 마지막 접속 정보와 생성/수정 정보
- 계정 활성/비활성 여부
- 관리자 권한 여부
- 중복 사용자 ID 여부

## 6. 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 사용자 목록 조회 (우선순위: P1)

관리자는 사용자 목록과 계정 상태를 확인한다.

**관련 기능 요구사항**: FR-001, FR-002, FR-003, FR-004, FR-005

**이 우선순위의 이유**: 사용자 관리는 계정 현황 파악에서 시작한다.

**독립 테스트**: 관리자만 사용자 목록을 볼 수 있고 필터가 동작하는지 확인한다.

**허용 시나리오**:

1. **Given** 관리자 권한 사용자가 로그인되어 있다, **When** 사용자 관리 메뉴를 선택한다, **Then** 사용자 목록이 표시된다.
2. **Given** 사용자 목록이 표시되어 있다, **When** 역할 필터를 선택한다, **Then** 해당 역할 사용자만 표시된다.

### 사용자 스토리 2 - 사용자 추가와 수정 (우선순위: P2)

관리자는 사용자를 추가하거나 기본 정보를 수정한다.

**관련 기능 요구사항**: FR-006, FR-007, FR-008, FR-011

**이 우선순위의 이유**: 운영자는 신규 사용자 투입과 역할 변경을 처리할 수 있어야 한다.

**독립 테스트**: 추가/수정 입력, 필수값 오류, 중복 사용자 ID 오류를 확인한다.

**허용 시나리오**:

1. **Given** 사용자 추가 화면이 열려 있다, **When** 필수 정보를 입력하고 저장한다, **Then** 새 사용자가 추가 가능한 상태로 표시된다.
2. **Given** 중복 사용자 ID가 입력되어 있다, **When** 저장을 시도한다, **Then** 중복 오류가 표시된다.

### 사용자 스토리 3 - 사용자 비활성화 (우선순위: P2)

관리자는 더 이상 사용하지 않는 계정을 비활성화한다.

**관련 기능 요구사항**: FR-009, FR-010, FR-012

**이 우선순위의 이유**: 접근 권한 회수는 보안과 운영 안정성에 중요하다.

**독립 테스트**: 비활성화 동작과 자기 계정 위험 경고를 확인한다.

**허용 시나리오**:

1. **Given** 활성 사용자가 선택되어 있다, **When** 관리자가 비활성화를 실행한다, **Then** 계정 상태가 비활성으로 표시된다.
2. **Given** 관리자가 자기 계정을 변경하려 한다, **When** 위험 동작을 실행한다, **Then** 경고가 표시된다.

### 엣지 케이스

- 모든 관리자 계정이 비활성화되는 상황은 경고되어야 한다.
- 사용자명이 길어도 목록이 깨지지 않아야 한다.
- 비활성 계정은 로그인 가능 계정으로 오해되지 않아야 한다.

## 7. 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 관리자는 2번 이하의 조작으로 사용자 관리 화면에 진입할 수 있다.
- **SC-002**: 관리자는 3초 이내에 활성/비활성 계정 수를 파악할 수 있다.
- **SC-003**: 중복 사용자 ID는 저장 전에 표시된다.
- **SC-004**: 위험한 자기 계정 변경은 확인 없이 진행되지 않는다.
- **SC-005**: 비관리자는 메뉴와 화면 내용을 볼 수 없다.

## 8. 가정 및 미정 사항

### 가정

- MVP는 mock 사용자 목록과 mock 저장 흐름으로 진행한다.
- tester는 관리자, tester1은 비관리자 계정으로 검증한다.

### 미정 사항

- 비밀번호 정책과 계정 잠금 정책은 후속 보안 정책에서 정한다.
