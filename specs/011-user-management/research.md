# 리서치: 사용자 관리

## 결정 1: 사용자관리 MVP는 frontend mock-first로 진행한다

**Decision**: `tester / tester123` 관리자 mock 계정에서는 사용자관리 mock service를 사용하고, `tester1 / tester123` 비관리자 mock 계정에서는 접근 차단을 검증한다. tester 계열이 아닌 계정은 실제 API service 경계를 호출하는 구조를 유지한다.

**Rationale**: 현재 프로젝트의 로그인 정책은 tester/tester1만 mock으로 우회하고 나머지는 실제 API 경로를 타도록 정리되어 있다. 사용자관리도 같은 원칙을 따라야 mock 범위가 운영 경로로 번지지 않는다.

**Alternatives considered**:
- 모든 계정에서 mock 사용: 실제 API 전환 시 경계가 불명확해져 제외
- backend API를 먼저 구현: 현재 MVP와 디자이너 협업 흐름에 맞지 않아 제외

## 결정 2: 사용자 목록은 Tabulator 기반 그리드로 설계한다

**Decision**: 사용자 목록은 기존 `frontend/src/lib/tabulator` wrapper를 활용하는 그리드 중심 화면으로 설계한다.

**Rationale**: 사용자는 검색, 필터, 정렬, 페이지 탐색, 행 선택이 자연스러운 업무시스템 데이터다. 프로젝트에는 이미 Tabulator 기반 공통 모듈이 있어 신규 테이블 구현보다 기존 기반을 쓰는 편이 일관적이다.

**Alternatives considered**:
- 단순 HTML table: 업무시스템 수준의 정렬/필터/페이지 요구를 반복 구현해야 해 제외
- 카드 목록: 사용자관리처럼 행 단위 비교가 중요한 화면에 부적합해 제외

## 결정 3: 계정 상태와 재직 상태를 분리한다

**Decision**: `AccountStatus`는 활성/잠금/비활성을 표현하고, `EmploymentStatus`는 재직/휴직/퇴사를 표현한다.

**Rationale**: 퇴사자는 로그인 불가여야 하지만 이력과 개인화 참조가 남아 있을 수 있다. 계정 잠금은 보안상 임시 조치이고 퇴사 처리는 인사/운영 상태이므로 분리해야 상태 의미가 명확하다.

**Alternatives considered**:
- 단일 status 필드: 잠금, 비활성, 퇴사를 혼합하면 UI와 권한 판단이 모호해져 제외

## 결정 4: 삭제보다 비활성/퇴사 처리를 우선한다

**Decision**: 사용자 삭제는 즉시 삭제가 아니라 삭제 요청 흐름으로 두고, 기본 안내는 비활성화 또는 퇴사 처리를 우선한다.

**Rationale**: 사용자 데이터는 권한, 감사, 개인화 설정, 이벤트 처리 이력과 연결될 수 있다. 업무시스템에서는 계정 삭제가 참조 무결성과 운영 이력에 영향을 줄 수 있어 신중한 흐름이 필요하다.

**Alternatives considered**:
- 즉시 삭제: 이력 참조와 마지막 관리자 보호에 위험이 있어 제외
- 삭제 기능 제외: 사용자가 요구한 삭제 니즈를 충족하지 못해 제외

## 결정 5: 개인화 설정은 보유 여부와 처리 선택까지만 다룬다

**Decision**: 사용자관리에서는 개인화 설정의 보유 여부, 유지/초기화 선택만 다루고 실제 영상그리드 개인화 상세 편집은 002 또는 후속 권한/개인화 기능에서 다룬다.

**Rationale**: 사용자 데이터는 개인화 기능의 기준 데이터지만, 사용자관리 화면이 개인화 편집 화면까지 포함하면 범위가 과도하게 커진다.

**Alternatives considered**:
- 사용자관리에서 개인화 상세 편집 포함: 002 라이브 대시보드와 권한 정책 범위를 침범해 제외
