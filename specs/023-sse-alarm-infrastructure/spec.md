# 기능 명세: 실시간 알람 SSE 인프라

**기능 브랜치**: `023-sse-alarm-infrastructure`  
**작성일**: 2026-10-16  
**상태**: 구현 준비 완료

## 1. 기능 개요

운영자는 모니터링 화면을 열어 둔 상태에서 새 알람을 수동 새로고침 없이 받아야 한다. 시스템은 로그인한 사용자별 실시간 알람 채널을 제공하고, 알람 발생 시 구조화된 이벤트를 전달하며, 연결 끊김과 재연결을 안전하게 처리해야 한다.

## 2. 기능 요구사항

- **FR-001**: 시스템은 인증된 사용자가 자신의 실시간 알람 스트림을 구독할 수 있게 해야 한다.
- **FR-002**: 시스템은 인증되지 않은 스트림 요청을 거부하고 알람 데이터가 노출되지 않게 해야 한다.
- **FR-003**: 시스템은 사용자별로 알람 이벤트를 격리하여 다른 사용자의 이벤트를 전달하지 않아야 한다.
- **FR-004**: 시스템은 알람 이벤트에 이벤트 ID, 이벤트 종류, 알람 본문, 발생 시각을 포함해야 한다.
- **FR-005**: 시스템은 연결이 유휴 상태일 때 heartbeat를 보내 연결 생존을 확인할 수 있게 해야 한다.
- **FR-006**: 시스템은 정상 종료, 전송 실패, 클라이언트 연결 종료 시 해당 구독을 정리해야 한다.
- **FR-007**: 프론트엔드는 인증 정보를 포함해 스트림을 연결하고, 연결 종료 시 제한된 지수 백오프로 재연결해야 한다.
- **FR-008**: 프론트엔드는 중복 구독을 만들지 않으며, 구독 해제 시 네트워크 요청과 재연결 예약을 모두 종료해야 한다.
- **FR-009**: 시스템은 향후 실제 알람 생성원이 호출할 수 있는 사용자 대상 이벤트 발행 경계를 제공해야 한다.
- **FR-010**: 본 기능은 현재 이벤트 저장소나 알람 생성 로직을 새로 만들지 않고, 기존 mock-first 범위를 유지해야 한다.
- **FR-011**: 시스템은 브라우저 SSE 구독과 모델 서버 알람 수신을 하나의 알람 도메인과 `AlarmController`에서 제공해야 한다.
- **FR-012**: 모델 서버는 공통 알람 수신 endpoint로 warning을 보내고, `source`, `type`, `severity`, 카메라, 설명, 발생 시각, metadata로 업무 종류를 구분해야 한다.
- **FR-013**: 모델 서버 알람 수신은 전용 service key로 인증하고, 유효하지 않은 요청은 알람을 전달하지 않아야 한다.
- **FR-014**: 인증된 모델 서버의 알람은 현재 연결된 모든 사용자 SSE 구독에 fan-out되어야 한다.
- **FR-015**: 모델 서버 알람 수신은 기존 알람 source 자체나 저장된 영상 소스를 삭제/변경하지 않아야 한다.

## 3. 제외 범위

- 알람 이벤트의 영속 저장, 조회/검색, acknowledge 처리
- Redis/Kafka 등 외부 브로커와 다중 인스턴스 간 fan-out
- 브라우저 Notification 권한 요청 및 소리 재생
- RTSP ingest, AI inference, 미디어 서버 구현

## 4. 사용자 시나리오 및 테스트

### 사용자 스토리 1 - 실시간 알람 수신 (P1)

운영자로서 모니터링 화면을 열면 새 알람을 즉시 받아 현재 화면의 알람 목록과 배지에 반영하고 싶다.

**인수 시나리오**

1. **Given** 유효한 로그인 세션이 있고 스트림을 구독하면, **When** 해당 사용자에게 알람이 발행될 때, **Then** 알람 payload가 한 번 전달된다.
2. **Given** 두 사용자가 각각 구독 중이면, **When** 사용자 A에게 알람이 발행될 때, **Then** 사용자 B는 그 알람을 받지 않는다.
3. **Given** 스트림이 일정 시간 이벤트 없이 유지되면, **When** heartbeat 주기가 도래할 때, **Then** 연결 유지용 heartbeat가 전달된다.

### 사용자 스토리 2 - 연결 복구 (P1)

운영자로서 일시적인 네트워크 장애 뒤에도 페이지를 새로고침하지 않고 알람 수신을 계속하고 싶다.

**인수 시나리오**

1. **Given** 구독 연결이 끊기면, **When** 재연결 지연 시간이 지나면, **Then** 프론트엔드는 정해진 최대 횟수 안에서 다시 연결한다.
2. **Given** 구독 해제가 완료되면, **When** 이전 연결이 종료 이벤트를 발생시키면, **Then** 새 재연결이 생성되지 않는다.

### 사용자 스토리 3 - 보안 및 자원 정리 (P1)

운영자로서 인증되지 않은 사용자의 알람 접근이 차단되고, 화면을 닫은 뒤 서버에 유령 연결이 남지 않기를 원한다.

**인수 시나리오**

1. **Given** bearer 인증 정보가 없거나 만료되었으면, **When** 스트림을 요청할 때, **Then** 서버는 401을 반환하고 스트림을 열지 않는다.
2. **Given** 클라이언트가 연결을 종료하면, **When** 서버가 종료를 감지하면, **Then** 해당 사용자 구독이 제거된다.

## 5. 경계 조건

- 동일 사용자의 여러 탭은 각각 독립적인 구독으로 동작한다.
- 이벤트 전송 중 클라이언트가 사라져도 다른 구독의 전송은 영향을 받지 않는다.
- 연결이 이미 닫힌 구독으로 발행해도 발행 호출자는 예외를 직접 처리하지 않고 계속 동작한다.
- 애플리케이션 재시작 시 인메모리 연결과 미전달 이벤트는 복구 대상이 아니다.
- 이벤트 payload는 민감한 인증 토큰을 포함하지 않는다.

## 6. 성공 기준

- **SC-001**: 인증된 사용자의 이벤트 발행부터 브라우저 수신까지 로컬 환경에서 1초 이내에 완료된다.
- **SC-002**: 인증된 스트림 구독에서 30초 이상 이벤트가 없어도 heartbeat가 최소 한 번 전달된다.
- **SC-003**: 100개의 동시 구독에서 사용자 간 이벤트 혼선이 0건이다.
- **SC-004**: 연결 종료 후 서버의 해당 구독 수가 1 heartbeat 주기 이내에 감소한다.
- **SC-005**: 프론트엔드 테스트와 백엔드 테스트가 통과하고 기존 이벤트/인증 테스트가 회귀하지 않는다.

## 7. 가정

- 현재 애플리케이션은 단일 백엔드 인스턴스에서 실행되므로 인메모리 fan-out을 MVP로 사용한다.
- SSE 요청은 기존 `/api/**` 인증 interceptor를 통과한다.
- 브라우저의 `EventSource`는 Authorization 헤더를 설정할 수 없으므로 프론트는 fetch 기반 SSE reader를 사용한다.
- 기본 heartbeat 주기는 15초, 최대 재연결 시도 횟수는 5회로 둔다.
