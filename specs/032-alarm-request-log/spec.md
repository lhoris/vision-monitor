# 알람 요청 원장과 수신자 로그 분리

**기능 브랜치**: `032-alarm-request-log`  
**작성일**: 2026-11-25  
**상태**: 초안

## 1. 개요

알람 발생 사실과 사용자별 알람 처리 결과를 분리한다. 알람 발생 시 `TB_M26_ALARM_REQ`에 요청 원장 1건을 만들고, 내부 팬아웃 워커가 알람 기준의 수신자별 `TB_M26_ALARM_LOG`를 생성한다. 이후 채널 전송 워커가 로그의 앱 알람·메일·팀즈 상태를 처리한다. 등록 시점에 활성 알람 기준이 없으면 요청을 생성하지 않고 명확한 오류로 거절한다.

## 2. 사용자 시나리오

### US1. 유효한 알람 요청 원장 생성 (P1)

발생 주체는 알람 코드와 이벤트 정보를 제출하고, 시스템은 활성 알람 기준을 확인한 뒤 요청 원장을 저장한다.

**검증 기준**

1. 활성 알람 기준이 존재하면 요청 원장 1건이 생성된다.
2. 동일한 원천 이벤트가 반복되어도 요청 원장이 중복 생성되지 않는다.
3. 요청 원장 생성은 수신자별 로그 생성과 분리되어도 원천 정보가 보존된다.

### US2. 수신자별 로그 분배 (P1)

팬아웃 워커는 요청 원장의 알람 기준과 사용자별 수신 설정을 읽어 수신자별 상세 로그를 생성한다.

**검증 기준**

1. 활성 수신자마다 동일 요청에 대한 로그가 최대 1건 생성된다.
2. 앱·메일·팀즈 수신 설정에 따라 각 채널 상태가 초기화된다.
3. 공동 확인 알람의 로그는 동일한 요청 ID로 연결된다.

### US3. 알람 기준 누락 차단 (P1)

등록 요청의 알람 코드가 없거나 비활성 기준이면 요청을 저장하지 않고 기준 누락 오류를 반환한다.

**검증 기준**

1. 존재하지 않는 코드로는 요청 원장이 생성되지 않는다.
2. 비활성 알람 기준으로는 요청 원장이 생성되지 않는다.
3. 발생 주체가 원인을 식별할 수 있는 오류 코드와 메시지를 받는다.

### US4. 채널 전송 및 확인 처리 연계 (P2)

기존 채널 전송 워커와 확인 기능은 수신자별 로그를 기준으로 계속 동작한다.

**검증 기준**

1. 팬아웃이 완료된 로그는 기존 앱 알람 SSE 전송 대상이 된다.
2. 채널별 전송 상태와 사용자 확인 상태가 서로 독립적으로 유지된다.
3. 공동 확인 시 같은 요청의 관련 로그가 함께 확인 처리된다.

## 3. 기능 요구사항

- **FR-001**: 시스템은 알람 발생 1건을 요청 원장 1건으로 저장해야 한다.
- **FR-002**: 요청 원장은 활성 알람 기준 ID를 필수로 가져야 한다.
- **FR-003**: 활성 알람 기준이 없으면 요청 원장 저장을 거부해야 한다.
- **FR-004**: 요청 원장은 원천 이벤트 ID를 이용해 중복 생성을 방지해야 한다.
- **FR-005**: 팬아웃 워커는 요청 원장과 알람 기준의 수신 설정을 이용해 수신자별 로그를 생성해야 한다.
- **FR-006**: 수신자별 로그는 요청 ID와 사용자 ID 조합으로 중복 생성되지 않아야 한다.
- **FR-007**: 알람 로그는 앱·메일·팀즈 채널 상태와 사용자 확인 상태를 각각 보존해야 한다.
- **FR-008**: 채널 전송 워커는 팬아웃된 알람 로그만 처리해야 한다.
- **FR-009**: 기존 알람 조회·확인·SSE 기능은 알람 로그 상세를 기준으로 동작해야 한다.
- **FR-010**: 기존 데이터의 호환성을 고려한 마이그레이션 경로를 제공해야 한다.

## 4. 범위 제외

- 별도 알람 데몬 프로세스 추가
- 메일·팀즈 실제 외부 연동 구현
- 전송 실패 자동 재시도
- 알람 요청 상태 컬럼을 이용한 별도 상태 머신

## 5. 데이터 개념

- **알람 기준**: 알람 코드와 분류·확인 방식을 정의하는 `TB_M26_ALARM_RULE`.
- **알람 요청 원장**: 발생한 알람의 공통 정보와 기준 참조를 보존하는 `TB_M26_ALARM_REQ`.
- **알람 로그 상세**: 수신자별 확인 상태와 채널 전송 상태를 보존하는 `TB_M26_ALARM_LOG`.

알람 요청은 생성 후 변경하지 않는 원장으로 취급한다. 요청에 상태를 추가하지 않고, 상세 로그의 존재 여부와 채널 상태로 후속 처리를 판단한다. 중복 방지는 요청 원천 이벤트 ID와 수신자 조합의 유일성으로 보장한다.

## 6. 성공 기준

- 유효한 알람 요청 1건이 원장 1건과 수신자별 상세 로그로 추적된다.
- 잘못된 알람 코드 요청은 데이터베이스에 원장이나 상세 로그를 남기지 않는다.
- 동일 원천 이벤트를 반복 전송해도 중복 원장·중복 수신자 로그가 생성되지 않는다.
- Spring Boot 재기동 후 미분배 요청이 수신자 로그로 정상 분배된다.
- 기존 알람 화면과 SSE 수신 기능의 사용자 동작이 유지된다.

## 7. 가정 및 제약

- 모델 서버가 Spring Boot 중단 중에도 DB에 직접 요청 원장을 기록할 수 있도록 동일한 DB 계약을 문서화한다.
- 요청 원장에는 활성 알람 기준 ID를 저장하며, 기준 코드만 전달되는 입력은 저장 전 기준 조회로 검증한다.
- 팬아웃과 채널 전송은 Spring Boot 내부의 별도 스케줄 작업으로 구성하되 별도 프로세스는 두지 않는다.
