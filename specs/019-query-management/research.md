# 연구 기록: 쿼리 관리 메뉴

## 결정 1: 기존 Query 테이블과 조회 서비스를 재사용한다

- **결정**: 신규 테이블을 만들지 않고 `TB_M26_METADATA_QUERY`를 관리 대상으로 사용한다.
- **근거**: `V011__create_metadata_query_tables.sql`에 Query ID, SQL Text, 파라미터/결과 Schema, 제한시간, 사용 여부와 프로젝트 표준 Audit 항목이 이미 정의되어 있다.
- **대안**: 관리 전용 테이블을 추가하는 방식은 메타데이터 실행 기능과 중복 저장 및 동기화 문제를 만들기 때문에 제외한다.

## 결정 2: 실행 API와 관리 API를 분리한다

- **결정**: 기존 메타데이터 화면용 조회·실행 계약은 유지하고, 등록·수정·활성화·논리 삭제는 관리자 전용 관리 계약으로 분리한다.
- **근거**: 일반 사용자에게 SQL 전문이 노출되지 않아야 하고, 기존 화면 확대 보기의 Query ID 계약을 깨지 않아야 한다.
- **대안**: 기존 목록 API에 관리자 CRUD를 모두 추가하는 방식은 권한 및 응답 데이터 경계를 흐리므로 사용하지 않는다.

## 결정 3: SQL 검증은 저장 시점과 실행 시점에 모두 적용한다

- **결정**: 저장 시 기본 구문 검증을 수행하고, 실제 실행 시에도 기존 조회 전용 검증을 다시 수행한다.
- **근거**: 데이터가 외부 변경이나 기존 Migration으로 입력될 수 있으므로 저장 시점 검증만으로는 충분하지 않다.
- **대안**: 실행 시점 검증만 적용하면 관리 화면에서 잘못된 Query가 저장되는 문제가 남는다.

## 결정 4: 참조 중 Query는 삭제 대신 비활성화를 허용한다

- **결정**: 메타데이터 섹션이 참조 중인 Query의 논리 삭제는 거부하고, 비활성화는 허용한다.
- **근거**: 기존 섹션의 논리 참조를 보존하면서 신규 사용을 차단할 수 있다.
- **대안**: 강제 삭제는 기존 화면의 Query 오류와 참조 이력 손실을 유발할 수 있어 제외한다.

## 결정 5: Mock fallback은 Query 관리 기능의 저장 경로에 사용하지 않는다

- **결정**: Query 관리 메뉴는 실제 backend API와 DB를 사용하며, 목록·저장 실패를 Mock 데이터로 대체하지 않는다.
- **근거**: 관리자가 저장했다고 인식한 Query가 DB에 존재하지 않으면 화면 확대 보기와 운영 데이터가 불일치한다.
- **대안**: 기존 메타데이터 조회 화면의 fallback은 별도 기능이므로 이번 메뉴의 영속화 경로에는 적용하지 않는다.
