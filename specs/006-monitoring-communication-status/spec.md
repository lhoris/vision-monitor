# 기능 명세서: 모니터링 통신 현황

**기능 브랜치**: `006-monitoring-communication-status`

**작성일**: 2026-08-17

**상태**: 초안

**변경 추적**: 문서 변경 이력은 Git 커밋 이력을 기준으로 한다.

**입력**: 왼쪽 사이드바 관리자 메뉴의 "모니터링 통신 현황"에 대한 기능명세서를 Spec Kit 흐름으로 작성한다는 사용자 요청, 현재 000 앱 기본 뼈대의 관리자 메뉴 구조, 현재 관리자 placeholder route

> 이 문서는 한국어로 작성한다. 기술 용어, API 이름, 파일 경로, 코드 식별자는 원문 또는 영문 표기를 유지할 수 있다.
> 기능 명세서는 "무엇을 제공해야 하는가"를 정의한다. 구현 방식, 컴포넌트 구조, DTO/API 세부사항, 파일 경로는 plan.md 또는 contracts/에서 다룬다.

> **기능 개요 - Agent 요약**
>
> 모니터링 통신 현황은 관리자 권한 사용자가 영상 모니터링에 필요한 통신 상태를 한 화면에서 확인하는 운영 점검 기능이다. 관리자는 카메라, 영상 수신, 모니터링 처리, 이벤트 전달처럼 실시간 감시에 영향을 주는 연결 상태를 정상/지연/장애로 구분해 보고, 장애가 있는 항목을 빠르게 찾아 원인을 추적할 수 있어야 한다. 이 화면은 상태 확인과 점검 흐름에 집중하며, 통신 주소 수정, 제어 연동 상태, 모델 재가동 같은 조치 기능은 별도 관리자 메뉴로 분리한다. MVP에서는 mock 데이터 기반으로 화면과 상태 판단 기준을 먼저 정의하고, 실제 외부 시스템 연동은 후속 범위로 둔다.

## 2. 기능 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 관리자 권한 사용자는 왼쪽 사이드바의 관리자 메뉴에서 모니터링 통신 현황 화면에 진입할 수 있어야 한다.
- **FR-002**: 관리자 권한이 없는 사용자는 모니터링 통신 현황 메뉴와 화면에 접근할 수 없어야 한다.
- **FR-003**: 시스템은 모니터링에 필요한 통신 대상 목록을 사용자가 한눈에 확인할 수 있게 표시해야 한다.
- **FR-004**: 시스템은 각 통신 대상의 현재 상태를 정상, 지연, 장애, 확인 불가 중 하나로 구분해 표시해야 한다.
- **FR-005**: 시스템은 각 통신 대상의 이름, 구분, 관련 공정 또는 장비, 마지막 정상 확인 시각, 최근 점검 결과를 표시해야 한다.
- **FR-006**: 사용자는 상태, 통신 구분, 공정 또는 장비 조건으로 통신 대상 목록을 필터링할 수 있어야 한다.
- **FR-007**: 사용자는 필터를 초기화하고 전체 통신 대상 목록으로 돌아갈 수 있어야 한다.
- **FR-008**: 시스템은 장애 또는 지연 상태인 통신 대상 수를 화면 상단에서 요약해 보여야 한다.
- **FR-009**: 사용자는 특정 통신 대상을 선택해 상세 상태와 최근 점검 이력을 확인할 수 있어야 한다.
- **FR-010**: 시스템은 선택된 통신 대상의 상세 영역에서 장애 원인 후보 또는 운영자가 확인해야 할 점검 포인트를 표시해야 한다.
- **FR-011**: 사용자는 통신 상태를 수동으로 다시 확인하는 동작을 실행할 수 있어야 한다.
- **FR-012**: 시스템은 수동 재확인 중인 상태와 재확인 완료 결과를 사용자가 이해할 수 있게 표시해야 한다.
- **FR-013**: 시스템은 통신 대상이 없거나 필터 결과가 비어 있는 상태를 사용자가 이해할 수 있게 표시해야 한다.
- **FR-014**: 시스템은 통신 상태 정보를 가져오지 못한 경우에도 화면 전체가 무너지지 않고 실패 상태와 재시도 가능성을 표시해야 한다.
- **FR-015**: 시스템은 모니터링 통신 현황 화면에서 통신 주소 설정, 제어 연동 통신 현황, 모델 재가동 기능을 직접 수행하지 않아야 한다.

## 3. 제외 범위 *(필수)*

- 실제 Spring Boot 통신 상태 API 구현은 MVP 범위에서 제외한다.
- 실제 DB migration, 통신 상태 이력 저장소 설계, 운영 로그 영구 저장은 MVP 범위에서 제외한다.
- 실제 VMS, Media Server, RTSP ingest, AI inference, WebSocket/SSE 상태 수신 연동은 MVP 범위에서 제외한다.
- 통신 주소 추가/수정/삭제는 "기타 주소 설정 현황" 또는 별도 설정 기능 범위로 분리한다.
- 제어 시스템 연동 상태 확인은 "제어 연동 통신 현황" 기능 범위로 분리한다.
- 모델 재가동과 영상 모델 추가는 각각 별도 관리자 메뉴 범위로 분리한다.
- 장애 알림 규칙 설정, 알림 발송 정책, 운영 리포트 생성은 이번 기능 범위에서 제외한다.

## 4. UI/UX 요구사항

- **UX-001**: 화면 상단에는 전체 통신 대상 수, 정상 수, 지연 수, 장애 수, 확인 불가 수가 요약되어야 한다.
- **UX-002**: 장애와 지연 상태는 색상만으로 구분하지 않고 상태 텍스트와 아이콘 또는 배지를 함께 제공해야 한다.
- **UX-003**: 목록, 필터, 상세 정보의 관계가 명확해야 하며 현재 선택된 통신 대상이 분명히 보여야 한다.
- **UX-004**: 상세 영역은 운영자가 바로 확인할 수 있도록 최근 점검 시각, 최근 응답 상태, 점검 포인트를 우선 표시해야 한다.
- **UX-005**: 수동 재확인 동작은 중복 실행 여부와 진행 중 상태가 명확해야 한다.
- **UX-006**: 필터 결과 없음, 전체 대상 없음, 상태 조회 실패는 서로 다른 메시지로 구분되어야 한다.
- **UX-007**: theme1, theme2, theme3에서 상태 배지, 요약 카드, 상세 텍스트, 빈 상태 메시지가 읽을 수 있게 표시되어야 한다.
- **UX-008**: 운영 모니터 화면이므로 불필요하게 큰 장식 요소보다 밀도 있고 스캔하기 쉬운 정보 배치를 우선해야 한다.

## 5. 필요한 정보

- 사용자는 통신 대상 이름과 구분을 확인할 수 있어야 한다.
- 사용자는 통신 대상이 어느 공정, 설비, 카메라, 모니터링 기능과 관련되는지 확인할 수 있어야 한다.
- 사용자는 각 통신 대상의 현재 상태와 마지막 정상 확인 시각을 확인할 수 있어야 한다.
- 사용자는 최근 점검 결과, 최근 장애 또는 지연 사유, 운영 점검 포인트를 확인할 수 있어야 한다.
- 시스템은 정상, 지연, 장애, 확인 불가 상태를 구분해야 한다.
- 시스템은 관리자 권한 여부에 따라 메뉴 노출과 화면 접근 가능 여부를 판단해야 한다.

## 6. 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 모니터링 통신 상태 요약 확인 (우선순위: P1)

관리자는 모니터링 통신 현황 화면에 진입해 전체 연결 상태와 장애/지연 건수를 즉시 확인한다.

**관련 기능 요구사항**: FR-001, FR-002, FR-003, FR-004, FR-005, FR-008

**이 우선순위의 이유**: 이 기능의 핵심은 관리자가 현재 모니터링 인프라가 정상인지 빠르게 판단하는 것이다.

**독립 테스트**: 관리자 권한으로 화면에 진입했을 때 통신 대상 목록과 상태 요약이 표시되고, 비관리자 권한으로는 접근할 수 없는지 확인한다.

**허용 시나리오**:

1. **Given** 관리자 권한 사용자가 로그인되어 있다, **When** 사이드바에서 모니터링 통신 현황 메뉴를 선택한다, **Then** 통신 상태 요약과 통신 대상 목록이 표시된다.
2. **Given** 통신 대상 목록에 정상, 지연, 장애 상태가 섞여 있다, **When** 화면 상단 요약을 확인한다, **Then** 상태별 건수가 목록과 일치하게 표시된다.
3. **Given** 관리자 권한이 없는 사용자가 로그인되어 있다, **When** 사이드바 메뉴를 확인한다, **Then** 모니터링 통신 현황 메뉴가 표시되지 않는다.

---

### 사용자 스토리 2 - 장애 또는 지연 대상 찾기 (우선순위: P1)

관리자는 상태와 공정 조건으로 목록을 좁혀 장애 또는 지연 상태인 통신 대상을 빠르게 찾는다.

**관련 기능 요구사항**: FR-006, FR-007, FR-008, FR-013

**이 우선순위의 이유**: 통신 대상이 많아질수록 장애 대상만 빠르게 선별하는 기능이 운영 효율에 직접적인 영향을 준다.

**독립 테스트**: 상태와 공정 필터를 적용하고 초기화했을 때 목록과 요약이 현재 조건에 맞게 갱신되는지 확인한다.

**허용 시나리오**:

1. **Given** 통신 대상 목록이 표시되어 있다, **When** 사용자가 장애 상태 필터를 선택한다, **Then** 장애 상태인 통신 대상만 표시된다.
2. **Given** 상태 필터와 공정 필터가 적용되어 있다, **When** 사용자가 필터 초기화를 선택한다, **Then** 전체 통신 대상 목록으로 돌아간다.
3. **Given** 현재 필터 조건에 맞는 통신 대상이 없다, **When** 목록 영역을 확인한다, **Then** 필터 결과가 없음을 알리는 상태가 표시된다.

---

### 사용자 스토리 3 - 통신 대상 상세와 점검 이력 확인 (우선순위: P2)

관리자는 특정 통신 대상을 선택해 최근 상태 변화와 점검 포인트를 확인한다.

**관련 기능 요구사항**: FR-009, FR-010, FR-014

**이 우선순위의 이유**: 목록에서 이상 상태를 확인한 뒤 운영자가 실제 조치 방향을 판단하려면 상세 정보가 필요하다.

**독립 테스트**: 목록에서 항목을 선택했을 때 상세 영역이 선택 항목 기준으로 갱신되고, 실패 상태가 목록 전체를 깨뜨리지 않는지 확인한다.

**허용 시나리오**:

1. **Given** 통신 대상 목록이 표시되어 있다, **When** 사용자가 특정 항목을 선택한다, **Then** 상세 영역에 선택 항목의 최근 점검 결과와 점검 포인트가 표시된다.
2. **Given** 선택된 통신 대상이 장애 상태다, **When** 상세 정보를 확인한다, **Then** 장애 원인 후보 또는 운영 점검 포인트가 표시된다.
3. **Given** 상세 상태 조회가 실패했다, **When** 상세 영역을 확인한다, **Then** 목록은 유지되고 상세 영역에 실패 상태와 재시도 가능성이 표시된다.

---

### 사용자 스토리 4 - 수동 재확인 실행 (우선순위: P3)

관리자는 의심되는 통신 대상의 상태를 수동으로 다시 확인하고 결과를 확인한다.

**관련 기능 요구사항**: FR-011, FR-012

**이 우선순위의 이유**: 자동 갱신이 없거나 최신 상태가 의심되는 상황에서 운영자가 현재 상태를 다시 확인할 수 있어야 한다.

**독립 테스트**: 수동 재확인을 실행했을 때 진행 중 상태와 완료 결과가 구분되어 표시되는지 확인한다.

**허용 시나리오**:

1. **Given** 통신 대상 상세 정보가 표시되어 있다, **When** 사용자가 수동 재확인을 실행한다, **Then** 해당 대상이 확인 중 상태로 표시된다.
2. **Given** 수동 재확인이 완료되었다, **When** 결과가 표시된다, **Then** 최신 상태와 확인 시각이 갱신된다.
3. **Given** 수동 재확인이 실패했다, **When** 결과가 표시된다, **Then** 실패 메시지와 다시 시도할 수 있는 상태가 표시된다.

### 엣지 케이스

- 관리자 권한이 없는 사용자가 관리자 route에 직접 접근하면 접근 제한 또는 기본 업무 화면 이동으로 처리되어야 한다.
- 통신 대상 목록이 비어 있으면 필터 결과 없음과 구분되는 전체 대상 없음 상태를 표시해야 한다.
- 전체 상태 조회가 실패해도 사용자가 오류를 이해하고 재시도할 수 있어야 한다.
- 수동 재확인 중 같은 대상을 다시 확인하려는 경우 중복 실행이 사용자에게 혼란을 주지 않아야 한다.
- 긴 통신 대상 이름이나 긴 점검 메시지가 목록과 상세 레이아웃을 깨뜨리지 않아야 한다.
- 상태별 색상이 테마에 따라 달라져도 상태 의미가 유지되어야 한다.

## 7. 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 관리자 권한 사용자는 로그인 후 2번 이하의 조작으로 모니터링 통신 현황 화면에 진입할 수 있다.
- **SC-002**: 관리자는 화면 진입 후 3초 이내에 장애 또는 지연 상태의 존재 여부를 판단할 수 있다.
- **SC-003**: 관리자는 3개 이하의 필터 조작으로 특정 상태와 공정에 해당하는 통신 대상만 확인할 수 있다.
- **SC-004**: 관리자는 목록에서 통신 대상을 선택한 뒤 1초 이내에 해당 대상의 상세 상태와 점검 포인트를 확인할 수 있다.
- **SC-005**: 관리자는 수동 재확인을 실행한 뒤 진행 중, 성공, 실패 상태를 구분해 이해할 수 있다.
- **SC-006**: theme1, theme2, theme3에서 정상, 지연, 장애, 확인 불가 상태가 텍스트와 시각 표현으로 명확히 구분된다.
- **SC-007**: 비관리자 사용자는 사이드바에서 모니터링 통신 현황 메뉴를 볼 수 없고 직접 접근해도 화면 내용을 확인할 수 없다.

## 8. 가정 및 미정 사항

### 가정

- MVP는 mock 데이터 기준으로 진행한다.
- "모니터링 통신"은 영상 모니터링 기능이 정상 동작하는 데 필요한 카메라, 영상 수신, 모니터링 처리, 이벤트 전달 계열의 상태 확인을 의미한다.
- 관리자는 `tester / tester123` mock 계정처럼 관리자 권한이 있는 사용자로 간주한다.
- 비관리자는 `tester1 / tester123` mock 계정처럼 관리자 권한이 없는 사용자로 간주한다.
- 통신 주소 수정과 실제 장애 조치는 다른 관리자 메뉴 또는 후속 기능에서 다룬다.

### 미정 사항

- 실제 운영 환경에서 표시할 통신 대상의 최종 분류와 명칭은 외부 시스템 계약 확정 후 조정한다.
- 상태 자동 갱신 주기와 장기 이력 보관 기간은 실제 운영 정책 확정 후 후속 명세에서 정한다.
