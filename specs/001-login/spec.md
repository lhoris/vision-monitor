# 기능 명세서: 로그인

**기능 브랜치**: `001-login`

**작성일**: 2026-08-16

**상태**: 초안

**변경 추적**: 문서 변경 이력은 Git 커밋 이력을 기준으로 한다.

**입력**: 현재 구현된 로그인 화면과 tester mock 로그인 유지, 비-tester 계정 로그인 API 호출 요구사항

> 이 문서는 한국어로 작성한다. 기술 용어, API 이름, 파일 경로, 코드 식별자는 원문 또는 영문 표기를 유지할 수 있다.
> 기능 명세서는 "무엇을 제공해야 하는가"를 정의한다. 구현 방식, 컴포넌트 구조, DTO/API 세부사항, 파일 경로는 plan.md 또는 contracts/에서 다룬다.

> **기능 개요 - Agent 요약**
>
> 로그인 기능은 사용자가 Vision Monitor에 접근하기 전에 계정과 비밀번호를 입력해 인증 상태를 만드는 진입 화면이다. MVP에서는 디자이너와의 frontend 중심 작업을 유지하기 위해 `tester / tester123` 계정은 backend 의존 없이 mock 로그인으로 통과시킨다. 단, tester가 아닌 계정은 아직 backend/DB가 완성되지 않았더라도 로그인 API를 실제 호출해야 하며, 실패 시 사용자가 이해할 수 있는 오류를 표시해야 한다. 인증 성공 후 사용자는 라이브 메인 화면으로 이동하고, 인증되지 않은 사용자는 보호된 화면 대신 로그인 화면으로 이동해야 한다.

## 1. 참고 이미지 및 원문 자료

| 상태 | 자료 | 설명 | 비고 |
|------|------|------|------|
| active | 현재 구현된 로그인 화면 | AI Vision Monitor 로그인 card, username/password 입력, demo credential 안내 | 구현 기준 화면 |
| active | 대화 원문 요구사항 | tester 계정 mock 로그인 유지, tester가 아닌 경우에만 로그인 API 호출 | 최신 인증 동작 기준 |

## 2. 기능 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 사용자는 로그인 화면에서 계정명과 비밀번호를 입력할 수 있어야 한다.
- **FR-002**: 시스템은 계정명이 비어 있으면 로그인을 시도하지 않고 계정명 필수 오류를 표시해야 한다.
- **FR-003**: 시스템은 비밀번호가 비어 있으면 로그인을 시도하지 않고 비밀번호 필수 오류를 표시해야 한다.
- **FR-004**: 시스템은 `tester / tester123` 입력 시 backend API를 호출하지 않고 mock 인증으로 로그인 성공 처리해야 한다.
- **FR-004a**: `tester / tester123` mock 계정은 관리자 메뉴를 확인할 수 있는 관리자 권한을 가져야 한다.
- **FR-005**: 시스템은 계정명이 `tester`이고 비밀번호가 일치하지 않으면 backend API를 호출하지 않고 로그인 실패를 표시해야 한다.
- **FR-006**: 시스템은 계정명이 `tester`가 아닌 경우 로그인 API를 호출해야 한다.
- **FR-007**: 로그인 API가 성공하면 시스템은 인증 상태와 사용자 정보를 저장하고 라이브 메인 화면으로 이동해야 한다.
- **FR-008**: 로그인 API가 실패하거나 응답이 유효하지 않으면 시스템은 로그인 실패 오류를 표시해야 한다.
- **FR-009**: 로그인 요청 중에는 사용자가 중복 제출을 인지할 수 있도록 진행 상태를 표시해야 한다.
- **FR-010**: 인증되지 않은 사용자가 보호된 화면에 접근하면 로그인 화면으로 이동해야 한다.
- **FR-011**: 사용자가 로그아웃하면 인증 상태가 해제되고 로그인 화면으로 이동해야 한다.

## 3. 제외 범위 *(필수)*

- MVP에서는 실제 사용자 DB 설계와 DB migration을 제외한다.
- MVP에서는 실제 Spring Boot 인증 controller/service/repository 구현을 제외한다.
- MVP에서는 refresh token, session 만료 연장, 비밀번호 재설정, 계정 잠금 정책을 제외한다.
- MVP에서는 역할별 권한 화면 제어를 001 범위에 포함하지 않는다.
- 002 라이브 메인 화면과 003 화면 확대 보기의 세부 기능은 로그인 성공 이후 화면으로만 연결한다.

## 4. UI/UX 요구사항

- **UX-001**: 로그인 화면은 제품명과 로그인 목적이 명확히 보이는 단일 진입 화면이어야 한다.
- **UX-002**: tester demo credential은 개발/시연 환경에서 사용자가 확인할 수 있어야 한다.
- **UX-003**: 필수값 오류와 인증 실패 오류는 입력 form 근처에서 명확하게 보여야 한다.
- **UX-004**: 로그인 요청 중 버튼은 진행 상태를 표시하고 중복 클릭을 방지해야 한다.
- **UX-005**: theme1, theme2, theme3에서 입력값, 오류 메시지, demo credential 텍스트가 명확하게 보여야 한다.

## 5. 필요한 정보

- 사용자는 계정명과 비밀번호를 입력한다.
- 시스템은 tester mock 계정 여부를 판단해야 한다.
- 시스템은 비-tester 계정의 로그인 API 성공/실패 결과를 판단해야 한다.
- 시스템은 인증된 사용자 id, username, 인증 token을 보관해야 한다.
- 시스템은 인증 상태에 따라 로그인 화면과 보호 화면 접근을 분기해야 한다.

## 6. 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - tester mock 계정으로 로그인 (우선순위: P1)

개발/시연 사용자는 backend 없이도 tester 계정으로 로그인해 라이브 메인 화면에 접근한다.

**관련 기능 요구사항**: FR-001, FR-002, FR-003, FR-004, FR-007, FR-010

**이 우선순위인 이유**: frontend 중심 MVP와 디자이너 협업을 계속 가능하게 하는 최소 인증 흐름이다.

**독립 테스트**: `tester / tester123`으로 로그인하면 API 호출 없이 인증 성공 처리되고 `/live`로 이동하는지 확인한다.

**수용 시나리오**:

1. **Given** 사용자가 로그인 화면에 있다, **When** `tester / tester123`을 입력하고 로그인한다, **Then** 시스템은 API를 호출하지 않고 로그인 성공 처리한다.
2. **Given** 사용자가 인증되지 않았다, **When** 보호된 화면에 접근한다, **Then** 로그인 화면으로 이동한다.

---

### 사용자 스토리 2 - 비-tester 계정으로 로그인 API 호출 (우선순위: P2)

운영 계정 사용자는 backend 준비 상태와 무관하게 로그인 API 호출 경로를 통해 인증을 시도한다.

**관련 기능 요구사항**: FR-006, FR-007, FR-008, FR-009

**이 우선순위인 이유**: 실제 인증 연동으로 넘어가기 위한 frontend 호출 경계가 필요하다.

**독립 테스트**: `operator` 같은 비-tester 계정으로 로그인하면 `/auth/login` 요청이 발생하고, 실패 시 오류가 표시되는지 확인한다.

**수용 시나리오**:

1. **Given** 사용자가 비-tester 계정을 입력했다, **When** 로그인을 실행한다, **Then** 시스템은 로그인 API를 호출한다.
2. **Given** 로그인 API가 실패한다, **When** 요청이 종료된다, **Then** 시스템은 인증 상태를 만들지 않고 오류를 표시한다.
3. **Given** 로그인 API가 성공한다, **When** 유효한 사용자와 token이 반환된다, **Then** 시스템은 인증 상태를 저장하고 라이브 메인 화면으로 이동한다.

---

### 사용자 스토리 3 - 로그인 실패와 로그아웃 (우선순위: P3)

사용자는 잘못된 tester 비밀번호나 API 실패를 명확히 인지하고, 인증 후에는 로그아웃할 수 있다.

**관련 기능 요구사항**: FR-005, FR-008, FR-011

**이 우선순위인 이유**: 인증 상태가 잘못 유지되면 보호 화면 접근 흐름이 깨진다.

**독립 테스트**: tester의 잘못된 비밀번호는 API 호출 없이 실패하고, 로그아웃 시 인증 상태와 token이 제거되는지 확인한다.

**수용 시나리오**:

1. **Given** 사용자가 `tester`와 잘못된 비밀번호를 입력했다, **When** 로그인을 실행한다, **Then** 시스템은 API를 호출하지 않고 실패를 표시한다.
2. **Given** 사용자가 로그인되어 있다, **When** 로그아웃한다, **Then** 인증 상태가 해제되고 로그인 화면으로 이동한다.

### 엣지 케이스

- 계정명 앞뒤 공백은 필수값 판단에서 제거되어야 한다.
- 비밀번호가 비어 있으면 tester 여부와 관계없이 API 호출을 하지 않아야 한다.
- 비-tester API 호출이 네트워크 오류로 실패해도 화면이 멈추지 않아야 한다.
- 로그인 API 응답에 token 또는 user가 없으면 실패로 처리해야 한다.
- 로그인 요청 중 사용자가 버튼을 반복 클릭해도 중복 제출이 눈에 띄게 제한되어야 한다.

## 7. 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 사용자는 `tester / tester123`으로 backend 없이 로그인해 2번 이하의 조작으로 라이브 메인 화면에 진입할 수 있다.
- **SC-002**: 비-tester 계정 로그인 시도는 항상 로그인 API 호출을 1회 이상 발생시킨다.
- **SC-003**: tester 계정의 올바른 mock 로그인과 잘못된 비밀번호 실패는 모두 API 호출 없이 판정된다.
- **SC-004**: 로그인 실패 시 사용자는 같은 화면에서 오류 원인을 확인하고 다시 시도할 수 있다.
- **SC-005**: 인증되지 않은 상태에서는 보호된 화면이 노출되지 않는다.

## 8. 가정 및 미정 사항

### 가정

- `tester / tester123`은 개발/시연용 mock 계정으로 유지한다.
- 비-tester 로그인 API는 아직 실패할 수 있지만, frontend는 실제 호출 경로를 유지한다.
- 로그인 성공 후 기본 이동 대상은 `/live`이다.
- token 저장은 MVP에서 브라우저 저장소를 사용한다.

### 미정 사항

- 실제 backend 인증 endpoint의 최종 응답 shape는 후속 backend 설계에서 확정한다.
