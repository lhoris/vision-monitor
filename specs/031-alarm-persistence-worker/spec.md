# 알람 저장 및 내부 전송 워커

**기능 브랜치**: `031-alarm-persistence-worker`  
**작성일**: 2026-11-25  
**상태**: 초안

## 1. 개요

일반 알람과 모델 알람을 모두 알람 로그에 저장하고, Spring Boot 내부 워커가 저장된 로그를 기준으로 수신자별 앱 알람·메일·팀즈 알림봇 전송을 처리한다. Spring Boot가 일시적으로 중단되어도 모델 서버는 DB에 알람을 직접 기록할 수 있으며, 재기동 후 워커가 미처리 알람을 처리한다.

## 2. 사용자 시나리오

### US1. 알람 기준별 수신자와 채널 관리 (P1)

관리자는 알람 기준을 선택하고 하위 수신자 목록에서 사용자 또는 권한을 지정한다. 각 수신자에 대해 앱 알람, 메일, 팀즈 알림봇 수신 여부를 각각 설정한다.

**검증**

1. 알람 기준을 선택하면 해당 기준의 수신자 목록과 채널 설정을 확인할 수 있다.
2. 수신자를 추가·수정하면 동일한 알람 유형과 사용자 조합으로 중복 설정이 생성되지 않는다.
3. 상위 알람 기준 화면에는 DB 저장 여부나 수신대상범위가 표시되지 않는다.

### US2. 모든 알람의 DB 저장 (P1)

일반 알람은 Spring Boot API를 통해, 모델 알람은 모델 서버가 직접 DB에 기록할 수 있어야 한다. 발생 주체와 관계없이 알람은 저장되어야 하며 Spring Boot가 중단된 동안 생성된 모델 알람도 재기동 후 조회할 수 있어야 한다.

**검증**

1. Spring Boot API로 등록한 알람이 알람 로그에 저장된다.
2. 모델 서버가 정해진 DB 계약으로 등록한 알람이 저장된다.
3. 동일한 모델 이벤트가 재전송되어도 고유 이벤트 ID로 중복 저장되지 않는다.

### US3. 채널별 내부 전송 처리 (P1)

Spring Boot 내부 워커는 `PENDING` 상태의 채널을 조회하여 수신자 설정에 따라 전송한다. 채널별 성공은 `SENT`, 실패는 `FAILED`, 사용하지 않는 채널은 `SKIPPED`로 남긴다. 실패 채널은 자동 재시도하지 않는다.

**검증**

1. Spring Boot가 재기동되면 중단 중 저장된 `PENDING` 알람이 처리된다.
2. 앱 알람 전송 후 해당 로그의 앱 채널 상태가 `SENT`로 바뀐다.
3. 전송 실패는 `FAILED`로 남고 자동 재시도되지 않는다.
4. 한 채널의 처리 결과가 다른 채널의 상태를 변경하지 않는다.

### US4. 사용자별·공동 확인 처리 (P2)

알람 전달 상태와 사용자의 확인 상태는 분리한다. 개별 확인 알람은 해당 사용자 로그만 확인 처리하고, 공동 확인 알람은 같은 그룹의 로그를 함께 확인 처리한다.

## 3. 기능 요구사항

- **FR-001**: 시스템은 알람 기준과 수신자 설정을 분리하여 관리해야 한다.
- **FR-002**: 알람 기준은 알람 코드, 명칭, 설명, 분류, 확인 범위만 관리해야 한다.
- **FR-003**: 수신자 설정은 사용자 또는 권한을 대상으로 앱 알람, 메일, 팀즈 알림봇 수신 여부를 개별 관리해야 한다.
- **FR-004**: 모든 알람은 DB 저장 대상이어야 하며 DB 저장 여부를 선택하는 설정을 제공하지 않아야 한다.
- **FR-005**: Spring Boot API와 모델 서버 직접 DB 입력은 동일한 알람 로그 필드 계약을 사용해야 한다.
- **FR-006**: 모델 서버 직접 입력은 고유 이벤트 ID를 제공하여 중복 저장을 방지해야 한다.
- **FR-007**: 알람 로그는 앱·메일·팀즈 채널별 상태를 각각 보유해야 한다.
- **FR-008**: 채널 상태는 외부에 `PENDING`, `SENT`, `FAILED`, `SKIPPED`로 관리하며, 동시성 제어를 위한 내부 일시 상태 `PROCESSING`을 허용한다.
- **FR-009**: 내부 워커는 `PENDING`만 처리하며 `FAILED`는 재시도하지 않아야 한다.
- **FR-010**: 내부 워커는 동일 채널을 한 번만 처리하도록 DB 원자적 선점 또는 동등한 동시성 제어를 사용해야 한다.
- **FR-011**: 앱 알람은 인증된 수신자에게만 SSE로 전달해야 한다.
- **FR-012**: 전송 상태와 알람 확인 상태는 서로 독립적으로 관리해야 한다.

## 4. 범위 제외

- 별도 알람 데몬 또는 메시지 큐 도입
- 메일·팀즈 외부 서비스의 인증정보 및 운영 환경 설정 확정
- 전송 실패 사유의 DB 저장
- 전송 실패 자동 재시도
- 알람 전달 이력용 별도 `ALARM_DELIVERY` 테이블

## 5. 데이터 핵심

- `TB_M26_ALARM_RULE`: 알람 기준
- `TB_M26_USER_ALERT_PREF`: 알람 기준별 수신자·채널 설정
- `TB_M26_ALARM_LOG`: 수신자별 알람 발생 이력과 채널별 전송 상태
- `SOURCE_EVENT_ID`: 모델 서버 재전송 중복 방지용 고유 이벤트 ID

## 6. 성공 기준

- Spring Boot 중단 중 모델 서버가 기록한 알람이 재기동 후 알람 화면에 표시된다.
- 한 알람의 앱·메일·팀즈 상태를 독립적으로 조회할 수 있다.
- `FAILED` 채널은 자동 재전송되지 않는다.
- 동일한 모델 이벤트가 중복 로그로 쌓이지 않는다.
- 기존 알람 확인 및 공동 확인 기능이 유지된다.

## 7. 가정

- 모델 서버는 DB 접속 권한과 동일한 알람 로그 입력 계약을 사용할 수 있다.
- 수신자별 로그를 유지하기 위해 `TB_M26_ALARM_LOG`는 수신자 단위 행을 사용할 수 있다.
- 메일·팀즈 전송 어댑터가 연결되지 않은 환경에서는 해당 채널을 `SKIPPED` 또는 `FAILED`로 명확히 처리한다.
