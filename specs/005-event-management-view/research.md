# 조사 결과: 알람 이력과 발생 영상

## 결정 1: 기존 알람 화면을 확장한다

- **결정**: 별도 녹화 화면을 새로 만들지 않고 기존 `/events` 화면을 알람 이력과 영상 확인 화면으로 확장한다.
- **근거**: 현재 화면에 필터, 목록, 상세, 확인 처리 흐름이 이미 있고 사용자의 업무 흐름도 알람 확인 중심이다.
- **대안**: 알람과 녹화를 별도 화면으로 분리하면 알람 시점과 영상을 함께 비교하기 어렵다.

## 결정 2: 녹화 전후 오프셋은 알람 규칙 설정에서 읽는다

- **결정**: 화면은 알람에 직접 고정된 시간값을 두지 않고 알람 규칙의 시작 전/종료 후 초 값을 사용한다.
- **근거**: 향후 알람 관리 화면에서 업무별로 설정을 변경할 수 있어야 한다.
- **대안**: 모든 알람에 동일한 고정 구간을 적용하면 공정과 모델별 운영 요구를 반영할 수 없다.

## 결정 3: 확인 상태는 사용자별로 분리한다

- **결정**: 알람 원본 상태와 사용자별 확인 상태를 분리한다.
- **근거**: 사용자 A가 확인해도 사용자 B의 미확인 업무가 사라지면 안 된다.
- **대안**: 알람 하나에 boolean 하나만 두는 방식은 다중 사용자 운영에 맞지 않는다.

## 결정 4: MVP는 mock-first로 구현한다

- **결정**: 실제 녹화/알람 API 대신 계약과 mock adapter로 화면을 먼저 검증한다.
- **근거**: 프로젝트 헌법과 기존 이벤트/녹화 화면이 같은 단계적 개발 방식을 사용한다.
- **대안**: backend와 녹화 서버를 동시에 구현하면 화면 요구사항 검증이 지연된다.
