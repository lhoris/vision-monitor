# 기능 명세서: 이벤트 관리

**기능 브랜치**: `005-event-management-view`

**작성일**: 2026-08-17

**상태**: 초안

**변경 추적**: 문서 변경 이력은 Git 커밋 이력을 기준으로 한다.

**입력**: 왼쪽 사이드바의 이벤트 메뉴에 대한 기능명세서를 Spec Kit 흐름으로 작성한다는 사용자 요청, 현재 구현된 이벤트 화면, 003 화면 확대 보기의 이벤트/알람 연계 요구사항

> 이 문서는 한국어로 작성한다. 기술 용어, API 이름, 파일 경로, 코드 식별자는 원문 또는 영문 표기를 유지할 수 있다.
> 기능 명세서는 "무엇을 제공해야 하는가"를 정의한다. 구현 방식, 컴포넌트 구조, DTO/API 세부사항, 파일 경로는 plan.md 또는 contracts/에서 다룬다.

> **기능 개요 - Agent 요약**
>
> 이벤트 관리는 운영자가 왼쪽 사이드바의 이벤트 메뉴에서 카메라와 시스템에서 발생한 이벤트를 한 화면에서 조회하고 확인 처리하는 기능이다. 라이브 메인 화면과 화면 확대 보기에서는 이벤트가 특정 영상 맥락 안에서 표시되지만, 이벤트 관리 화면은 전체 이벤트를 목록 중심으로 탐색하고 미확인 이벤트를 정리하는 운영 업무에 집중한다. 사용자는 심각도, 카메라, 이벤트 유형, 확인 상태, 기간 같은 조건으로 이벤트를 좁혀 보고, 선택한 이벤트의 상세 정보와 관련 카메라/녹화 연결 가능 여부를 확인할 수 있어야 한다. MVP는 mock 데이터를 기준으로 하며, 실제 알람 수신, 서버 push, 장기 이력 저장, 권한 정책 CRUD는 후속 범위로 분리한다.

## 2. 기능 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 사용자는 왼쪽 사이드바의 이벤트 메뉴에서 이벤트 관리 화면에 진입할 수 있어야 한다.
- **FR-002**: 시스템은 이벤트 목록을 발생 시각 기준으로 확인할 수 있게 표시해야 한다.
- **FR-003**: 사용자는 심각도, 카메라, 이벤트 유형, 확인 상태, 기간 조건으로 이벤트 목록을 필터링할 수 있어야 한다.
- **FR-004**: 사용자는 적용된 필터를 초기화하고 전체 이벤트 목록으로 돌아갈 수 있어야 한다.
- **FR-005**: 사용자는 이벤트 목록에서 특정 이벤트를 선택해 상세 정보를 확인할 수 있어야 한다.
- **FR-006**: 시스템은 이벤트 상세에서 발생 시각, 카메라, 이벤트 유형, 심각도, 설명, 확인 상태를 표시해야 한다.
- **FR-007**: 사용자는 미확인 이벤트를 단건 확인 처리할 수 있어야 한다.
- **FR-008**: 사용자는 현재 필터 결과 안의 미확인 이벤트를 일괄 확인 처리할 수 있어야 한다.
- **FR-009**: 시스템은 미확인 이벤트 수를 사용자가 빠르게 인지할 수 있게 표시해야 한다.
- **FR-010**: 시스템은 이벤트와 관련된 녹화 또는 화면 확대 보기로 이동 가능한 경우 그 연결 가능성을 표시해야 한다.
- **FR-011**: 시스템은 이벤트가 없거나 필터 결과가 비어 있는 상태를 사용자가 이해할 수 있게 표시해야 한다.
- **FR-012**: 시스템은 권한이 없는 이벤트의 상세 정보와 관련 영상 정보를 사용자에게 노출하지 않아야 한다.

## 3. 제외 범위 *(필수)*

- MVP에서는 실제 Spring Boot 이벤트 조회/확인 API 구현을 제외한다.
- MVP에서는 DB migration과 이벤트 이력 장기 저장 설계를 제외한다.
- MVP에서는 WebSocket/SSE 기반 실시간 이벤트 push를 제외한다.
- MVP에서는 알림 정책, 이벤트 룰, 권한 정책 CRUD 화면을 제외한다.
- MVP에서는 이벤트 통계 대시보드, 리포트, Excel/CSV 내보내기를 제외한다.
- MVP에서는 이벤트를 자동으로 조치하거나 설비 제어와 연동하는 기능을 제외한다.

## 4. UI/UX 요구사항

- **UX-001**: 이벤트 관리 화면은 목록, 필터, 상세 패널의 관계가 한눈에 이해되어야 한다.
- **UX-002**: 미확인 이벤트는 확인된 이벤트와 시각적으로 명확히 구분되어야 한다.
- **UX-003**: 심각도는 색상과 텍스트가 함께 표시되어 색상만으로 의미를 판단하지 않아도 되어야 한다.
- **UX-004**: 이벤트 상세 패널은 목록 선택과 즉시 연결되어 현재 선택된 이벤트를 명확히 보여야 한다.
- **UX-005**: 단건 확인과 일괄 확인은 실수로 실행했을 때 업무 혼선을 줄일 수 있도록 동작 범위가 명확히 보여야 한다.
- **UX-006**: 필터 결과가 없을 때는 단순 빈 표가 아니라 현재 조건에서 이벤트가 없음을 알 수 있어야 한다.
- **UX-007**: theme1, theme2, theme3에서 심각도 배지, 미확인 상태, 상세 정보, 빈 상태 메시지가 읽을 수 있게 표시되어야 한다.

## 5. 필요한 정보

- 사용자는 이벤트 발생 시각, 이벤트 유형, 심각도, 관련 카메라, 설명을 확인할 수 있어야 한다.
- 사용자는 이벤트 확인 여부와 미확인 이벤트 수를 확인할 수 있어야 한다.
- 사용자는 필터 조건과 현재 결과 개수를 확인할 수 있어야 한다.
- 시스템은 이벤트 없음, 필터 결과 없음, 권한 없음, 상세 조회 실패 상태를 구분해야 한다.
- 시스템은 이벤트가 특정 카메라나 녹화 구간과 연결될 수 있는지 판단해야 한다.

## 6. 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 이벤트 목록 조회와 필터링 (우선순위: P1)

운영자는 이벤트 메뉴에 진입해 전체 이벤트를 확인하고, 필요한 조건으로 목록을 좁혀 본다.

**관련 기능 요구사항**: FR-001, FR-002, FR-003, FR-004, FR-011

**이 우선순위인 이유**: 이벤트 관리의 핵심은 많은 이벤트 중 필요한 이벤트를 빠르게 찾는 것이다.

**독립 테스트**: 이벤트 메뉴로 이동한 뒤 심각도, 카메라, 이벤트 유형, 기간 필터를 적용하고 초기화할 수 있는지 확인한다.

**수용 시나리오**:

1. **Given** 사용자가 로그인 후 공통 앱 레이아웃을 보고 있다, **When** 사이드바에서 이벤트 메뉴를 선택한다, **Then** 이벤트 관리 화면이 표시된다.
2. **Given** 이벤트 목록이 표시되어 있다, **When** 사용자가 심각도와 카메라 조건을 선택한다, **Then** 조건에 맞는 이벤트만 목록에 표시된다.
3. **Given** 필터가 적용되어 있다, **When** 사용자가 필터 초기화를 선택한다, **Then** 전체 이벤트 목록으로 돌아간다.

---

### 사용자 스토리 2 - 이벤트 상세 확인 (우선순위: P1)

운영자는 목록에서 이벤트를 선택해 발생 상황과 관련 정보를 자세히 확인한다.

**관련 기능 요구사항**: FR-005, FR-006, FR-010, FR-012

**이 우선순위인 이유**: 이벤트 목록만으로는 원인 확인과 후속 조치 판단이 어렵기 때문에 상세 정보가 필요하다.

**독립 테스트**: 이벤트 목록에서 항목을 선택하면 상세 패널에 해당 이벤트 정보와 관련 영상 연결 가능 여부가 표시되는지 확인한다.

**수용 시나리오**:

1. **Given** 이벤트 목록이 표시되어 있다, **When** 사용자가 특정 이벤트를 선택한다, **Then** 상세 패널에 선택한 이벤트의 상세 정보가 표시된다.
2. **Given** 선택한 이벤트에 관련 녹화 구간이 있다, **When** 상세 정보를 확인한다, **Then** 관련 녹화 또는 화면 확대 보기로 이동 가능한 상태가 표시된다.
3. **Given** 사용자가 권한 없는 이벤트를 조회하려 한다, **When** 상세 결과가 표시된다, **Then** 제한된 상세 정보와 관련 영상 정보는 노출되지 않는다.

---

### 사용자 스토리 3 - 이벤트 확인 처리 (우선순위: P2)

운영자는 확인이 필요한 이벤트를 단건 또는 현재 필터 범위 안에서 일괄 확인 처리한다.

**관련 기능 요구사항**: FR-007, FR-008, FR-009

**이 우선순위인 이유**: 이벤트 확인 처리는 운영자가 조치 여부를 정리하고 미확인 이벤트를 줄이는 주요 업무다.

**독립 테스트**: 미확인 이벤트를 단건 확인 처리하고, 현재 필터 결과 안의 미확인 이벤트를 일괄 확인 처리했을 때 미확인 수와 상태 표시가 갱신되는지 확인한다.

**수용 시나리오**:

1. **Given** 미확인 이벤트가 있다, **When** 사용자가 해당 이벤트의 확인 처리를 실행한다, **Then** 이벤트 상태가 확인됨으로 바뀌고 미확인 수가 감소한다.
2. **Given** 필터 결과 안에 여러 미확인 이벤트가 있다, **When** 사용자가 일괄 확인을 실행한다, **Then** 현재 필터 결과 안의 미확인 이벤트만 확인됨으로 바뀐다.

---

### 사용자 스토리 4 - 빈 상태와 실패 상태 이해 (우선순위: P3)

운영자는 이벤트가 없거나 필터 결과가 없거나 상세 조회가 실패한 상황에서도 현재 상태를 명확히 이해한다.

**관련 기능 요구사항**: FR-011, FR-012

**이 우선순위인 이유**: 이벤트 화면은 운영 중 빈 상태와 제한 상태가 자주 발생할 수 있으므로 사용자가 오류와 정상 빈 상태를 구분해야 한다.

**독립 테스트**: 전체 이벤트 없음, 필터 결과 없음, 권한 없음, 상세 조회 실패 상태를 각각 표시해 사용자가 차이를 이해할 수 있는지 확인한다.

**수용 시나리오**:

1. **Given** 전체 이벤트가 없다, **When** 이벤트 화면이 표시된다, **Then** 전체 이벤트 없음 상태가 표시된다.
2. **Given** 이벤트는 있지만 현재 필터 조건에 맞는 이벤트가 없다, **When** 필터 결과가 표시된다, **Then** 필터 결과 없음 상태가 표시된다.
3. **Given** 이벤트 상세 조회에 실패했다, **When** 상세 영역이 표시된다, **Then** 목록은 유지되고 상세 영역에 실패 상태가 표시된다.

### 엣지 케이스

- 미확인 이벤트가 없으면 일괄 확인 동작은 표시되지 않거나 비활성 상태여야 한다.
- 필터 결과가 바뀌면 일괄 확인 대상 범위도 현재 필터 결과로 명확히 제한되어야 한다.
- 선택한 이벤트가 필터 변경 후 목록에서 제외되면 상세 패널은 선택 해제 또는 현재 조건 밖 상태를 표시해야 한다.
- 이벤트 설명이 길어도 목록 행과 상세 패널의 레이아웃이 깨지지 않아야 한다.
- 이벤트 상세 조회 실패가 발생해도 목록 필터와 현재 결과는 유지되어야 한다.

## 7. 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 사용자는 로그인 후 2번 이하의 조작으로 이벤트 관리 화면에 진입할 수 있다.
- **SC-002**: 사용자는 이벤트 목록에서 미확인 이벤트 수와 가장 높은 심각도의 이벤트를 3초 이내에 식별할 수 있다.
- **SC-003**: 사용자는 3개 이하의 조건 조작으로 원하는 카메라 또는 심각도 이벤트만 볼 수 있다.
- **SC-004**: 사용자는 목록에서 이벤트를 선택한 뒤 1초 이내에 상세 정보가 바뀐 것을 확인할 수 있다.
- **SC-005**: 사용자는 단건 확인 또는 현재 필터 범위 일괄 확인 후 미확인 수가 갱신된 것을 확인할 수 있다.
- **SC-006**: theme1, theme2, theme3에서 심각도, 확인 상태, 상세 정보, 빈 상태 메시지가 읽을 수 있게 표시된다.

## 8. 가정 및 미정 사항

### 가정

- MVP는 mock 데이터 기준으로 진행한다.
- 이벤트 관리는 사이드바의 `/events` 메뉴에 대응하는 독립 화면이다.
- 이벤트 확인 처리는 운영자가 이벤트를 봤거나 조치 대상으로 인지했다는 상태 표시로 간주한다.
- 이벤트와 관련 녹화 구간이 있는 경우 004 녹화영상 보기 또는 003 화면 확대 보기와 연결될 수 있다.
- 초기 초안에서는 이벤트 생성, 룰 설정, 알림 정책 관리는 다루지 않는다.

### 미정 사항

- 실제 운영에서 필요한 이벤트 보관 기간, 일괄 확인 권한, 확인 취소 가능 여부는 후속 명세에서 확정한다.
