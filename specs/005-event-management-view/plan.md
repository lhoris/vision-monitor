# 구현 계획: 알람 관리 화면 개정

**브랜치**: `005-event-management-view` | **작성일**: 2026-09-23 | **명세**: [spec.md](spec.md)

## 1. 계획 요약

기존 이벤트 목록 화면을 공정 운영용 알람 화면으로 확장한다. 상단 조회 조건과 알람 이력 그리드를 유지하되, 선택한 알람의 발생 시점 녹화 영상을 우측 상세 영역에서 확인하고, 사용자별 확인 처리와 오프셋 기반 영상 클립 다운로드를 제공한다.

이번 단계는 화면 퍼블리싱과 동작 검증을 위한 frontend mock-first 구현으로 진행한다. 알람 관리 화면 자체와 실제 녹화 서버 연동은 별도 범위로 두고, 향후 API로 교체 가능한 계약과 데이터 구조를 먼저 고정한다.

## 2. 기술 맥락

| 항목 | 결정 |
|---|---|
| 화면 | 기존 `Events.tsx`를 알람 관리 화면으로 확장 |
| 상태 | 기존 Redux `eventSlice`를 확장하여 조회, 선택, 확인 상태 관리 |
| 데이터 | 기존 `Event` 타입과 mock adapter를 알람 이력/녹화 클립 계약에 맞게 확장 |
| 영상 | 기존 `StreamPlayer`와 녹화 재생 세션 구조를 재사용 |
| 국제화 | 기존 `ko.json`, `en.json`의 `events` 영역을 알람 화면 용어로 보강 |
| 백엔드 | 이번 단계에서는 실제 API/DB를 추가하지 않음 |
| 테스트 | Vitest, React Testing Library, 기존 Events/Playback 테스트 패턴 활용 |
| 범위 | 알람 관리 화면의 오프셋 설정 UI는 제외하고, 설정값을 읽는 계약과 mock만 정의 |

## 3. 구현 범위

### 포함

- 공정, AI 모델, 판정 결과 조회 조건 및 조회 버튼
- 알람 이력 그리드와 선택 행 상태
- 우측 알람 상세 및 발생 시점 녹화 영상 영역
- 알람 규칙별 전후 녹화 오프셋 mock 설정
- 오프셋으로 계산한 녹화 구간 재생
- 오프셋으로 계산한 영상 클립 다운로드 mock 동작
- 현재 로그인 사용자 기준 확인/미확인 상태
- 확인 사용자와 확인 시각 표시
- 영상 없음, 부분 영상, 다운로드 실패 상태
- 한국어/영어 화면 문구와 접근성 레이블

### 제외

- 알람 관리 메뉴와 알람 규칙 CRUD 화면
- 실제 이벤트 수신, WebSocket/SSE push
- 실제 녹화 서버의 영상 생성/변환/다운로드 API
- DB 테이블과 Flyway migration
- 다른 사용자의 확인 상태를 직접 변경하는 관리자 기능

## 4. 설계

### 4.1 화면 구조

1. `AlarmQueryBar`: 공정, AI 모델, 판정 조건과 조회 동작
2. `AlarmHistoryTable`: 알람 이력, 판정, 영상 받기, 사용자별 확인 여부
3. `AlarmDetailPanel`: 선택 알람의 상세 정보, 확인 처리, 확인자/시각
4. `AlarmRecordingPanel`: 알람 시각 기준 전후 오프셋 녹화 재생 및 다운로드

기존 화면의 검색/심각도/카메라 필터는 업무상 필요한 경우 보조 조건으로 유지할 수 있으나, 새 화면의 주 조회 흐름은 공정/AI 모델/판정 조건을 우선한다.

### 4.2 알람과 녹화 구간

- 알람에는 발생 시각, 카메라/발생 위치, 공정, AI 모델명, 판정 결과를 가진다.
- 알람 규칙 설정은 `beforeSeconds`, `afterSeconds`를 제공한다.
- 재생 및 다운로드 구간은 `occurredAt - beforeSeconds`부터 `occurredAt + afterSeconds`까지 계산한다.
- 실제 녹화 가능 범위가 계산 구간보다 짧으면 실제 가능 구간을 사용하고 상태를 표시한다.
- 녹화 세션은 기존 `PlaybackSessionDto`와 호환되는 `playbackUrl`, `availableFrom`, `availableTo` 정보를 사용한다.

### 4.3 사용자별 확인 상태

- 공통 알람 데이터와 현재 사용자별 확인 데이터를 분리한다.
- 화면은 현재 로그인 사용자의 `acknowledged` 여부를 기준으로 상태와 미확인 건수를 계산한다.
- 확인 처리 시 현재 사용자 ID, 확인 시각을 기록하는 mock 결과를 반환한다.
- 다른 사용자의 확인 상태는 현재 사용자의 화면 상태에 영향을 주지 않는다.

## 5. 헌법 준수 점검

- **사용자 가치 우선**: 목록, 발생 영상, 판정, 확인 상태를 한 화면에서 연결해 운영 판단 시간을 줄인다.
- **기존 구조 존중**: 기존 `Events.tsx`, `eventSlice`, `eventService`, `StreamPlayer`를 확장한다.
- **Mock-First MVP**: 실제 backend/DB/녹화 서버 연동 없이 mock contract로 먼저 검증한다.
- **계약 우선**: 알람 상세, 녹화 구간, 확인 처리, 다운로드 결과의 shape를 별도 계약으로 고정한다.
- **독립 검증**: 조회, 영상 선택, 확인, 다운로드를 각각 컴포넌트/서비스 테스트로 검증한다.

## 6. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 알람 발생 시점과 녹화 시점 불일치 | 잘못된 장면 재생 | 계산된 구간과 실제 available 구간을 함께 표시 |
| 사용자별 확인 상태를 전역 boolean으로 처리 | 다른 사용자에게 잘못된 읽음 표시 | current-user acknowledgement를 별도 필드로 관리 |
| 영상이 없는 알람 | 우측 영역이 검게 비거나 오동작 | 명시적인 녹화 없음/부분 녹화 상태 제공 |
| 다운로드 범위가 전체 영상으로 확장 | 불필요한 대용량 다운로드 | clip range를 계약에서 필수로 유지 |
| 기존 이벤트 화면 테스트와 용어 충돌 | 회귀 테스트 실패 | 내부 event 식별자는 유지하고 화면 문구만 i18n으로 전환 |

## 7. 구현 순서

1. 알람/녹화/확인 데이터 타입과 mock fixture 확장
2. 조회 조건과 선택 상태를 Redux/service에 연결
3. 알람 이력 표와 상세/영상 영역을 컴포넌트로 분리
4. 오프셋 계산, 녹화 재생, 클립 다운로드 연결
5. 사용자별 확인 처리와 미확인 수 갱신 연결
6. 다국어/빈 상태/오류 상태/접근성 보강
7. 단위/컴포넌트 테스트와 frontend build 검증

## 8. 완료 기준

- 조회 조건으로 알람 목록을 재조회할 수 있다.
- 행 선택 시 동일 알람의 상세와 녹화가 표시된다.
- 오프셋 구간이 재생/다운로드 계약에 동일하게 적용된다.
- 확인 상태가 현재 로그인 사용자에게만 반영된다.
- 녹화 없음/부분 녹화/다운로드 실패 상태가 명확히 표시된다.
- 한국어와 영어에서 핵심 운영 문구가 모두 표시된다.
