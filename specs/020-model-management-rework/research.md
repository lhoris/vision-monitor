# 모델 관리 대개편 리서치

## 결정 1. 기본 보기와 편집 보기를 분리한다

- **결정**: 기본 진입 화면은 VM 카드와 프로세스 카드로 구성된 운영 대시보드로 제공하고, 등록·수정은 그리드 기반 관리 보기로 분리한다.
- **근거**: 운영자는 먼저 상태를 빠르게 파악해야 하며, 반복 입력에 적합한 그리드는 운영 현황을 표현하는 기본 화면으로 사용하기 어렵다.
- **검토한 대안**: 기존처럼 그리드만 제공하는 방식은 입력에는 유리하지만 VM과 프로세스의 계층 관계를 직관적으로 보여주기 어렵다.

## 결정 2. VM과 프로세스 상태를 분리한다

- **결정**: VM 연결 상태, 프로세스 실행 상태, 관리자 제어 요청 상태를 별도 필드와 표시 영역으로 관리한다.
- **근거**: VM은 연결되어 있지만 프로세스가 중지될 수 있고, 제어 요청 직후에는 실제 프로세스 상태가 아직 바뀌지 않을 수 있다.
- **검토한 대안**: 하나의 통합 상태로 표현하면 장애 원인과 요청 처리 상황을 구분하기 어렵다.

## 결정 3. 1차 구현은 Mock-First 계약 기반으로 진행한다

- **결정**: 화면과 상호작용은 기존 frontend service 경계를 유지하고 fixture/mock contract로 먼저 구현한다. Agent 실제 호출과 DB 스키마 확장은 후속 단계로 분리한다.
- **근거**: Agent 프로토콜과 원격 프로세스 실행 방식이 아직 확정되지 않았으며, 화면의 사용자 가치를 먼저 검증할 수 있다.
- **검토한 대안**: 미확정 Agent API를 먼저 구현하면 화면 요구사항 변경 시 backend와 migration까지 함께 재작업될 위험이 있다.

## 결정 4. 상태 갱신은 수동 새로고침과 자동 갱신을 분리한다

- **결정**: 대시보드는 상태 갱신 시각과 갱신 중 상태를 표시하고, 자동 갱신 주기는 계약에 포함하되 초기값은 현재 프로젝트의 조회 패턴을 기준으로 둔다.
- **근거**: 운영 화면은 최신 상태가 중요하지만, 갱신 중 기존 화면이 깜박이거나 제어 상태가 사라지면 안 된다.
- **미정**: 실제 운영 갱신 주기, stale 판정 시간, Agent heartbeat 주기는 운영 요구사항 확정 시 결정한다.
