# 기능 명세서: 통합 알람 관리

**기능 브랜치**: `025-alarm-management-settings`  
**작성일**: 2026-11-11  
**상태**: 구현 기준 확정

## 1. 목표와 핵심 원칙

관리자가 하나의 `알람 관리` 화면에서 알람 유형별 저장 정책, 수신자, 확인 방식, 채널을 관리한다. 사용자별 화면을 별도로 만들지 않으며, 알람 정책과 사용자별 예외 설정을 같은 화면 안에서 함께 다룬다.

- 알람 대분류는 `일반 알람`과 `모델 알람`으로 고정한다.
- 알람 유형의 기본 정책과 특정 사용자 예외 정책을 구분한다.
- 수신자와 채널 설정은 알람 발생 전에 적용한다.
- 공동 확인 알람은 한 수신자가 확인하면 같은 알람 그룹의 모든 수신자에게 확인 처리한다.
- 외부 메일/Teams 실제 발송은 이번 범위에서 제외하되, 정책 저장 구조와 push(SSE) 적용 기반은 제공한다.
- 새 물리 테이블은 만들지 않고 `TB_M26_CODE_DETAIL`, `TB_M26_USER_ALERT_PREF`, `TB_M26_ALARM_LOG`를 확장한다.

## 2. 기능 요구사항

- **FR-001**: 관리자는 알람 유형별 대분류, 표시명, 설명, 사용 여부를 확인할 수 있어야 한다.
- **FR-002**: 관리자는 알람 유형별 로그 저장 여부를 설정할 수 있어야 한다.
- **FR-003**: 관리자는 알람 유형별 수신자 방식을 `활성 최고관리자 전체` 또는 `지정 사용자`로 설정할 수 있어야 한다.
- **FR-004**: 지정 사용자 방식에서는 알람 유형별 수신자를 여러 명 선택하고 해제할 수 있어야 한다.
- **FR-005**: 관리자는 알람 유형별 확인 방식을 `공동 확인` 또는 `사용자별 확인`으로 설정할 수 있어야 한다.
- **FR-006**: 관리자는 알람 유형별 기본 `push`, `메일`, `Teams` 수신 여부를 설정할 수 있어야 한다.
- **FR-007**: 관리자는 사용자별로 알람 유형 수신 여부와 세 채널 수신 여부를 예외 지정할 수 있어야 한다.
- **FR-008**: 사용자별 설정이 없으면 알람 유형 기본 정책을 적용하고, 설정이 있으면 사용자별 설정을 우선 적용해야 한다.
- **FR-009**: push 수신 대상에게만 SSE와 알람 벨 알림을 전달해야 한다.
- **FR-010**: 로그 저장 여부와 사용자 수신 여부는 독립적으로 적용해야 한다.
- **FR-011**: 공동 확인 알람은 동일한 `ALARM_GROUP_ID`로 묶고 한 명의 확인이 그룹 전체에 반영되어야 한다.
- **FR-012**: 사용자별 확인 알람은 확인한 사용자의 로그만 확인 처리해야 한다.
- **FR-013**: 외부 채널 연동 전에도 메일/Teams 수신 설정을 저장하고 조회할 수 있어야 한다.
- **FR-014**: 관리자 권한이 없는 사용자는 통합 알람 관리 API와 화면을 사용할 수 없어야 한다.
- **FR-015**: 기존 알람 로그의 확인 상태와 표시 내용은 정책 변경으로 훼손되지 않아야 한다.

## 3. 화면 요구사항

- **UX-001**: 화면은 `알람 유형 정책`과 `사용자별 예외 설정`을 한 화면에서 제공한다.
- **UX-002**: 유형 행에는 대분류, 알람명, 설명, 저장 여부, 수신자 방식, 확인 방식, 기본 채널을 표시한다.
- **UX-003**: 유형을 선택하면 사용자 목록에서 수신자 여부와 세 채널을 설정할 수 있어야 한다.
- **UX-004**: `활성 최고관리자 전체` 방식에서는 사용자별 수신자 선택을 기본값으로 안내한다.
- **UX-005**: 저장 성공·실패를 명확히 안내하고, 변경 전 이탈을 방지한다.
- **UX-006**: 한국어 환경에서는 한글 표시명과 설명을 우선 사용한다.

## 4. 사용자 스토리

### 사용자 스토리 1 - 통합 알람 정책 관리 (P1)

관리자는 한 화면에서 유형별 저장, 수신자, 확인 방식, 기본 채널을 설정한다.

**수용 기준**

1. 신규 회원가입 요청을 `지정 사용자`, `공동 확인`, `push 수신`으로 저장할 수 있다.
2. 저장 후 화면을 다시 열어도 모든 정책이 유지된다.
3. 메일/Teams 수신 여부도 저장되지만 실제 외부 발송은 수행하지 않는다.

### 사용자 스토리 2 - 사용자별 예외 설정 (P1)

관리자는 선택한 알람 유형에 대해 특정 사용자의 수신 여부와 채널을 조정한다.

**수용 기준**

1. 지정 사용자 방식에서 선택한 사용자만 수신 대상으로 저장된다.
2. 특정 사용자의 push만 끄면 해당 사용자에게만 SSE가 전달되지 않는다.
3. 사용자별 설정이 없으면 유형 기본값으로 동작한다.

### 사용자 스토리 3 - 확인 범위 적용 (P1)

운영자는 공동 확인과 사용자별 확인을 알람 유형별로 선택한다.

**수용 기준**

1. 공동 확인 알람을 한 사용자가 확인하면 동일 그룹의 다른 수신자 알람도 확인된다.
2. 사용자별 확인 알람은 다른 수신자의 미확인 상태를 변경하지 않는다.

## 5. 데이터 및 호환성 원칙

- 새 테이블은 추가하지 않는다.
- `TB_M26_CODE_DETAIL`에 알람 유형 정책과 기본 채널/수신자 정보를 둔다.
- `TB_M26_USER_ALERT_PREF`에 `(USER_ID, ALARM_TYPE_CODE)`별 사용자 예외와 채널을 둔다.
- `TB_M26_ALARM_LOG`에 `ALARM_GROUP_ID`를 두어 공동 확인 범위를 표현한다.
- 기존 `EMAIL_ENABLED`, `SMS_ENABLED`는 하위 호환을 위해 유지하고 새 화면은 `PUSH_ENABLED`, `EMAIL_ENABLED`, `TEAMS_ENABLED`를 사용한다.

## 6. 제외 범위

- 이메일 서버, Microsoft Teams Webhook 등 외부 채널 실제 발송 연동
- 알람별 모델 임계값·감지영역·판정 알고리즘 설정
- 기존 알람 이력 화면의 검색·상세 개편

## 7. 성공 기준

- 관리자는 별도 사용자 화면 이동 없이 하나의 화면에서 정책과 사용자 예외를 저장할 수 있다.
- 신규 알람은 저장, 수신자, push 정책을 반영한다.
- 공동 확인과 사용자별 확인 결과가 알람 로그에서 구분된다.
