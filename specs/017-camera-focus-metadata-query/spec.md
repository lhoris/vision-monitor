# 화면 확대 보기 메타데이터 Query 구성

**기능 브랜치**: `017-camera-focus-metadata-query`

**작성일**: 2026-09-19

**상태**: 설계 확정 전 초안

**입력**: 화면 확대 보기에서 영상 소스마다 서로 다른 메타데이터 섹션을 구성하고, Query ID와 조회 주기로 동적 데이터를 표시해야 한다는 요구사항

## 1. 기능 개요

화면 확대 보기의 오른쪽 메타데이터 영역을 영상 소스별 구성 프로파일로 관리한다. 프로파일은 여러 개의 섹션으로 구성되며, 각 섹션은 텍스트, 그리드 또는 차트 형태로 표시된다.

운영자는 영상 소스에 필요한 섹션을 추가·수정·삭제하고 순서를 변경할 수 있다. 섹션은 정적 텍스트만 사용할 수도 있고, 등록된 Query ID를 통해 주기적으로 조회한 결과를 표시할 수도 있다.

이 기능의 데이터는 화면 개인화가 아니라 **영상 소스별 운영 메타데이터 구성**이다. 따라서 한 영상 소스의 섹션 구성을 변경해도 다른 영상 소스에는 영향을 주지 않는다.

## 2. 사용자와 권한

- 일반 사용자는 화면 확대 보기에서 해당 영상 소스의 메타데이터를 조회할 수 있어야 한다.
- 관리자 또는 메타데이터 구성 권한을 가진 사용자는 Query 정의와 영상 소스별 섹션 구성을 관리할 수 있어야 한다.
- Query SQL은 관리 화면에서 등록하지만 실행 시에는 조회 전용 정책을 적용해야 한다.
- tester 계정은 기존 Mock-First 정책에 따라 관리자 권한으로 구성 관리 흐름을 사용할 수 있어야 한다.

## 3. 범위

### 포함 범위

- Query 정의 등록·조회·수정·비활성화
- 영상 소스별 메타데이터 프로파일 관리
- 프로파일 내 섹션 추가·수정·삭제·복원
- 섹션 순서 변경 및 표시 여부 설정
- 텍스트·그리드·차트 섹션 표시
- Query 결과의 주기적 갱신
- 정적 텍스트와 Query 결과의 조합
- 섹션 단위 로딩·빈 결과·오류·이전 결과 유지 상태 표시
- 생성·수정 Audit 정보와 논리 삭제

### 제외 범위

- WebSocket/SSE 기반 실시간 Push
- Query SQL의 자동 생성
- INSERT, UPDATE, DELETE, DDL 등 변경성 SQL 실행
- 사용자가 임의의 DB에 접속하는 기능
- 섹션 데이터를 별도 이력 화면에서 분석하는 기능
- 차트 종류를 무제한으로 제공하는 고급 시각화 편집기

## 4. 핵심 용어

| 용어 | 정의 |
|---|---|
| Query 정의 | Query ID, 설명, 조회 SQL, 파라미터 규칙을 관리하는 등록 정보 |
| 프로파일 | 하나의 영상 소스에 적용되는 메타데이터 섹션 구성 묶음 |
| 섹션 | 화면 오른쪽 메타데이터 영역에 표시되는 하나의 구성 단위 |
| 정적 텍스트 | Query 없이 관리자가 직접 입력해 표시하는 텍스트 |
| Query 결과 | Query 실행 후 반환되는 컬럼 구조와 행 데이터 |
| 매핑 | Query 결과의 필드를 섹션 제목·값·그리드 컬럼·차트 계열에 연결하는 규칙 |

## 5. 기능 요구사항

### 5.1 Query 정의

- **FR-001**: 시스템은 고유한 Query ID를 가진 Query 정의를 등록할 수 있어야 한다.
- **FR-002**: Query 정의에는 명칭, 설명, SQL Text, 사용 여부, 조회 제한시간을 관리할 수 있어야 한다.
- **FR-003**: Query SQL은 조회 전용 문장만 등록·실행할 수 있어야 한다. 변경성 SQL이나 복수 문장은 거부해야 한다.
- **FR-004**: Query는 영상 소스 ID 등 허용된 파라미터를 바인딩할 수 있어야 하며, 문자열 치환 방식으로 파라미터를 주입해서는 안 된다.
- **FR-005**: 비활성화된 Query 또는 존재하지 않는 Query ID를 참조한 섹션은 실행하지 않고 구성 오류 상태를 표시해야 한다.
- **FR-006**: 사용 중인 Query 정의는 참조 중인 영상 소스와 섹션을 확인할 수 있어야 한다.

### 5.2 영상 소스별 프로파일

- **FR-007**: 시스템은 영상 소스마다 메타데이터 프로파일을 연결할 수 있어야 한다.
- **FR-008**: 하나의 영상 소스에는 하나의 활성 프로파일만 적용되어야 한다.
- **FR-009**: 프로파일이 없거나 비활성 상태이면 시스템 기본 프로파일을 표시할 수 있어야 한다.
- **FR-010**: 한 영상 소스의 프로파일 변경은 다른 영상 소스의 프로파일에 영향을 주지 않아야 한다.
- **FR-011**: 프로파일은 사용 여부와 기본 프로파일 여부를 관리할 수 있어야 한다.

### 5.3 섹션 구성

- **FR-012**: 관리자는 프로파일에 섹션을 추가할 수 있어야 한다.
- **FR-013**: 섹션 유형은 `TEXT`, `GRID`, `CHART` 중 하나여야 한다.
- **FR-014**: 관리자는 섹션 제목, 표시 여부, 표시 순서, Query ID, 조회 주기를 설정할 수 있어야 한다.
- **FR-015**: 관리자는 섹션을 수정하거나 논리 삭제할 수 있어야 한다.
- **FR-016**: 논리 삭제된 섹션은 복원할 수 있어야 한다.
- **FR-017**: 사용자는 화면 확대 보기에서 섹션을 드래그앤드롭으로 재배치할 수 있어야 하며, 변경된 순서는 해당 영상 소스 프로파일에 저장되어야 한다.
- **FR-018**: 섹션 순서는 연속된 숫자 또는 동일한 정렬 규칙으로 안정적으로 표시되어야 한다.
- **FR-019**: 모든 섹션이 삭제된 경우 빈 상태와 섹션 추가 진입점을 표시해야 한다.

### 5.4 텍스트 섹션

- **FR-020**: 텍스트 섹션은 Query 없이 정적 텍스트만 표시할 수 있어야 한다.
- **FR-021**: 텍스트 섹션은 Query 결과 없이도 기본 텍스트를 표시할 수 있어야 한다.
- **FR-022**: Query와 기본 텍스트가 함께 설정된 경우 Query 성공 시 결과를 표시하고, 조회 전·빈 결과·오류 시 기본 텍스트를 표시해야 한다.
- **FR-023**: 텍스트 섹션은 고정된 라벨 필드와 값 필드를 강제하지 않고, 설정된 텍스트를 자유로운 문장 형태로 표시할 수 있어야 한다.
- **FR-023a**: 텍스트 섹션은 `자유 텍스트(FREE)`와 `라벨-값(LABEL_VALUE)` 표시 형식을 제공해야 한다. 자유 텍스트는 textarea에 입력한 기본 텍스트를 우선 표시하고 Query와 독립적으로 저장할 수 있어야 한다.
- **FR-023b**: 라벨-값 표시 형식은 Query 결과의 라벨 필드와 값 필드를 선택해 행 단위로 표시해야 하며, Query와 두 필드 매핑이 없으면 저장할 수 없어야 한다.
- **FR-023c**: 기존 텍스트 섹션에 표시 형식이 저장되지 않은 경우, 라벨/값 매핑이 있으면 라벨-값 형식으로 호환 처리하고 그 외에는 자유 텍스트로 처리해야 한다.

### 5.5 그리드 섹션

- **FR-024**: 그리드 섹션은 Query 결과의 컬럼과 행을 표 형태로 표시해야 한다.
- **FR-025**: 관리자는 표시할 컬럼, 컬럼 제목, 순서, 값 형식을 설정할 수 있어야 한다.
- **FR-026**: 결과가 없으면 빈 결과 안내를 표시하고, 컬럼 구조가 잘못되면 해당 섹션만 오류 상태로 표시해야 한다.
- **FR-027**: 이벤트 데이터가 포함된 그리드는 재생 가능한 행에 재생 동작을 제공할 수 있어야 한다.

### 5.6 차트 섹션

- **FR-028**: 차트 섹션은 등록된 결과 필드를 기준으로 최소 하나 이상의 계열을 표시할 수 있어야 한다.
- **FR-029**: 관리자는 X축 필드, 값 필드, 계열명, 단위 또는 표시 형식을 설정할 수 있어야 한다.
- **FR-030**: 차트에 필요한 필드가 없으면 차트 전체가 아닌 해당 섹션만 오류 상태로 표시해야 한다.

### 5.7 조회와 상태

- **FR-031**: 섹션별 조회 주기는 최소 5초, 10초, 30초, 60초를 지원해야 한다.
- **FR-032**: 화면 진입 또는 영상 소스 변경 시 활성 섹션은 최초 조회를 수행해야 한다.
- **FR-033**: 이전 조회가 끝나지 않은 상태에서는 동일 섹션에 대한 중복 조회를 실행하지 않아야 한다.
- **FR-034**: 조회 중에는 `loading`, 성공 시 `success`, 결과가 없으면 `empty`, 오류 시 `error`, 새 조회 중 이전 결과를 유지하면 `stale` 상태를 표시해야 한다.
- **FR-035**: 한 섹션의 Query 오류가 다른 섹션의 표시와 조회를 중단시키지 않아야 한다.
- **FR-036**: 화면을 이탈하거나 영상 소스를 변경하면 이전 영상 소스의 조회 주기와 진행 중인 요청을 정리해야 한다.

### 5.8 Audit 및 논리 삭제

- **FR-037**: Query 정의, 프로파일, 섹션 등 관리성 데이터 테이블은 다음 Audit 항목을 반드시 가져야 한다.
  - `CREATED_OBJECT_TYPE`
  - `CREATED_OBJECT_ID`
  - `CREATED_PROGRAM_ID`
  - `CREATED_TIMESTAMP`
  - `LAST_UPDATED_OBJECT_TYPE`
  - `LAST_UPDATED_OBJECT_ID`
  - `LAST_UPDATED_PROGRAM_ID`
  - `LAST_UPDATED_TIMESTAMP`
  - `DATA_END_STATUS`
- **FR-038**: 삭제 동작은 물리 삭제가 아닌 `DATA_END_STATUS = 'Y'` 방식으로 처리해야 한다.
- **FR-039**: 기본 조회에서는 `DATA_END_STATUS = 'N'`인 데이터만 반환해야 한다.
- **FR-040**: Audit 사용자와 프로그램 정보는 현재 인증 사용자와 요청 기능을 기준으로 기록해야 한다.

## 6. 데이터 모델 요구사항

### 6.0 관계 제약 원칙

- 모든 테이블 간 관계는 논리적 참조로만 관리한다.
- 데이터베이스에 `FOREIGN KEY` 제약조건을 생성하지 않는다.
- 참조 컬럼은 명시적인 ID 컬럼명과 인덱스로 관계를 표현한다.
- 참조 대상의 존재 여부, 사용 여부, `DATA_END_STATUS`는 애플리케이션 서비스에서 검증한다.
- 논리 삭제된 참조 대상은 신규 프로파일·섹션·Query에서 참조할 수 없어야 한다.
- 테이블 생성·마이그레이션 순서는 물리 FK 의존성 없이 독립적으로 수행할 수 있어야 한다.

### 6.1 Query 정의

논리 테이블명: `TB_M26_METADATA_QUERY`

주요 속성:

- Query 식별자
- Query 명칭
- 설명
- 조회 SQL Text
- 파라미터 정의
- 조회 제한시간
- 사용 여부
- Audit 항목

### 6.2 영상 소스별 프로파일

논리 테이블명: `TB_M26_VIDEO_METADATA_PROFILE` (물리 FK 제약 없음)

주요 속성:

- 프로파일 식별자
- 영상 소스 식별자(논리 참조)
- 프로파일 명칭
- 기본 프로파일 여부
- 사용 여부
- Audit 항목

영상 소스와 프로파일의 연결은 유효한 활성 프로파일이 중복되지 않도록 보장해야 한다.

### 6.3 프로파일별 섹션

논리 테이블명: `TB_M26_VIDEO_METADATA_SECTION` (물리 FK 제약 없음)

주요 속성:

- 섹션 식별자
- 프로파일 식별자(논리 참조)
- 섹션 키
- 섹션 제목
- 섹션 유형
- 표시 순서
- 표시 여부
- Query 식별자(논리 참조)
- 조회 주기(초)
- 기본 텍스트
- 결과 매핑 정의
- Audit 항목

섹션 유형별 매핑 정보는 구조화된 설정 값으로 관리하되, 화면과 조회 계약에서 검증 가능한 형태여야 한다. 단순 문자열 파싱에 의존해서는 안 된다.

## 7. 사용자 시나리오 및 테스트

### 시나리오 1 - 영상 소스별 메타데이터 확인 (P1)

운영자는 화면 확대 보기에서 영상 소스를 선택하고, 해당 영상 소스에 연결된 메타데이터 프로파일을 확인한다.

**독립 테스트**: 서로 다른 두 영상 소스에 서로 다른 섹션 구성을 설정한 뒤 각각의 화면 확대 보기에서 올바른 섹션 조합이 표시되는지 확인한다.

1. **Given** 영상 소스 A에는 연결 상태 텍스트와 설정 그리드가 설정되어 있다.
2. **When** 사용자가 영상 소스 A의 화면 확대 보기에 진입한다.
3. **Then** 영상 소스 A의 프로파일 순서대로 섹션이 표시된다.
4. **And** 영상 소스 B의 설정은 표시되지 않는다.

### 시나리오 2 - Query 기반 주기 조회 (P1)

운영자는 섹션별 설정된 주기에 따라 최신 상태를 확인한다.

1. **Given** 섹션 A의 주기는 5초이고 섹션 B의 주기는 10초이다.
2. **When** 화면 확대 보기를 유지한다.
3. **Then** 섹션 A와 B는 서로의 주기를 사용하지 않고 각각 설정된 주기로 갱신된다.

### 시나리오 3 - 섹션 추가·삭제·순서 변경 (P1)

관리자는 영상 소스별로 필요한 섹션을 구성한다.

1. **Given** 프로파일에 텍스트, 설정 그리드, 이벤트 그리드가 있다.
2. **When** 관리자가 이벤트 그리드를 삭제하고 텍스트와 설정 그리드의 순서를 변경한다.
3. **Then** 화면에는 변경된 순서가 표시된다.
4. **And** 삭제된 섹션은 기본 조회에서 표시되지 않는다.
5. **And** 복원하면 삭제 전 섹션을 다시 사용할 수 있다.

### 시나리오 4 - 텍스트 섹션의 정적 기본값 (P1)

1. **Given** 텍스트 섹션에 Query 없이 기본 텍스트가 설정되어 있다.
2. **When** 화면 확대 보기에 진입한다.
3. **Then** 입력한 텍스트가 그대로 표시된다.
4. **Given** 텍스트 섹션에 Query와 기본 텍스트가 함께 설정되어 있다.
5. **When** Query 결과가 없거나 실패한다.
6. **Then** 기본 텍스트와 해당 섹션의 상태가 표시된다.

### 시나리오 5 - 섹션 오류 격리 (P1)

1. **Given** 세 개의 섹션 중 하나가 존재하지 않는 Query ID를 참조한다.
2. **When** 화면 확대 보기를 조회한다.
3. **Then** 잘못된 섹션에 오류 상태가 표시된다.
4. **And** 나머지 두 섹션은 정상적으로 표시되고 주기 조회를 계속한다.

## 8. 예외 및 경계 조건

- Query ID가 존재하지 않거나 비활성화된 경우
- SQL이 조회 전용 정책을 위반하는 경우
- 필수 결과 필드가 누락된 경우
- Query 결과가 0건인 경우
- Query 실행 제한시간을 초과한 경우
- 동일 섹션 조회가 아직 진행 중인 경우
- 영상 소스가 삭제되거나 비활성화된 경우
- 프로파일에 활성 섹션이 없는 경우
- 모든 섹션이 논리 삭제된 경우
- 관리자가 아닌 사용자가 구성 변경을 시도하는 경우
- 섹션 순서 값이 중복되거나 음수인 경우

## 9. 성공 기준

- **SC-001**: 운영자는 최대 3회의 화면 조작으로 특정 영상 소스의 메타데이터 구성 화면에 진입할 수 있다.
- **SC-002**: 사용자는 화면 확대 보기 진입 후 2초 이내에 정적 텍스트와 마지막 성공 Query 결과를 확인할 수 있다.
- **SC-003**: 5초, 10초, 30초, 60초로 설정된 섹션은 서로의 갱신 주기에 영향을 주지 않는다.
- **SC-004**: 하나의 섹션 Query가 실패해도 나머지 섹션은 계속 표시되고 갱신된다.
- **SC-005**: 관리자는 섹션 추가·삭제·복원·순서 변경을 완료한 뒤 화면을 다시 열어 동일한 구성을 확인할 수 있다.
- **SC-006**: 조회 전용 정책을 위반한 SQL은 실행되지 않고 사용자에게 구성 오류로 표시된다.
- **SC-007**: 모든 생성·수정·논리 삭제 데이터에서 생성자, 생성일시, 수정자, 수정일시, 종료 상태를 추적할 수 있다.

## 10. 가정 및 결정 사항

- MVP에서는 Query 실행 결과와 섹션 렌더링을 단계적으로 구현할 수 있으며, 초기 화면은 Mock 결과로 검증할 수 있다.
- 실제 DB Query 실행은 승인된 조회 전용 Query만 대상으로 한다.
- 데이터베이스 종류와 세부 SQL 실행 방식은 설계·구현 단계에서 기존 backend 저장소 규칙에 맞춰 확정한다.
- 사용자별 개인화 순서가 아니라 영상 소스별 운영 프로파일을 저장한다.
- 섹션 추가·삭제·순서 변경은 프로파일의 구성 데이터에 반영되며, 삭제는 논리 삭제한다.
- 차트는 초기에는 제한된 차트 유형과 명시적인 필드 매핑만 지원한다.
- DB 테이블명과 컬럼명은 본 명세의 논리 모델을 기반으로 `plan.md`의 데이터 모델 설계에서 최종 확정한다.
