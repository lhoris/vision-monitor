# 조사 결과: DB 세션 영속화

## 결정 1: 기존 DB 접근 패턴을 따른다

- **결정**: MariaDB와 Flyway를 유지하고, 프로젝트의 JPA 엔티티/Repository 패턴으로 세션 저장소를 구성한다.
- **근거**: 사용자, 권한, 공통코드 등 핵심 마스터 데이터가 같은 방식으로 관리되고 있으며 새 세션 데이터도 동일한 감사 규칙이 필요하다.
- **대안**: 순수 JDBC로만 구현하는 방식은 기존 도메인 구조와 테스트 패턴이 달라져 제외한다.

## 결정 2: DB에는 토큰 해시만 저장한다

- **결정**: 브라우저에 전달한 opaque token의 해시값을 저장하고, 요청 시 같은 방식으로 해시하여 비교한다.
- **근거**: DB 유출 시 원문 bearer token이 바로 재사용되는 위험을 줄인다.
- **대안**: 원문 토큰 저장은 구현은 단순하지만 인증 정보 노출 위험이 커서 제외한다.

## 결정 3: 8시간 절대 만료를 유지한다

- **결정**: 로그인 시각에서 8시간 후 만료되며 요청마다 만료 시각을 연장하지 않는다.
- **근거**: 현재 인메모리 구현의 동작과 사용자에게 안내한 세션 정책을 유지한다.
- **대안**: sliding expiration은 장기 미사용 세션 관리 정책이 추가로 필요하므로 이번 범위에서 제외한다.

## 결정 4: UK와 별도 INDEX를 만들지 않는다

- **결정**: PK 외 UK 및 별도 INDEX를 생성하지 않는다.
- **근거**: 프로젝트 운영 규칙과 이번 요구사항에 따른다.
- **주의**: 세션 수가 커질 때 조회 성능이 문제가 되면 별도 변경 요청으로 검토한다.
