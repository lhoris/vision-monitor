# DB 세션 영속화

**기능 브랜치**: `017-database-session-persistence`

**작성일**: 2026-09-22

**상태**: 초안

## 1. 기능 개요

백엔드 재기동이나 배포 이후에도 유효한 로그인 세션을 유지한다. 현재 메모리에만 저장되는 세션을 데이터베이스에 기록하여, 브라우저가 보관한 세션 토큰을 다시 검증할 수 있도록 한다.

세션은 로그인한 사용자와 만료 시각을 기준으로 유효성을 판단한다. 유효기간이 지난 세션이나 사용자가 명시적으로 로그아웃한 세션은 사용할 수 없어야 한다.

## 2. 기능 요구사항

- **FR-001**: 로그인 성공 시 시스템은 사용자별 세션을 생성하고 세션 정보를 영속적으로 저장해야 한다.
- **FR-002**: 저장되는 세션은 사용자 식별자, 토큰 식별 정보, 생성 시각, 만료 시각을 포함해야 한다.
- **FR-003**: 세션 저장 테이블의 이름은 `TB_M26_AUTH_SESSION`이어야 한다.
- **FR-004**: `TB_M26_AUTH_SESSION`의 Audit 항목은 기존 프로젝트 테이블과 동일하게 테이블 컬럼의 가장 앞에 배치해야 한다.
- **FR-005**: Audit 항목에는 생성, 최종 수정, 데이터 종료에 필요한 기존 표준 컬럼을 포함해야 한다.
- **FR-006**: 사용자 식별자와 세션 데이터 사이의 관계는 논리적으로만 관리하며, 물리적 FK 제약조건을 생성하지 않아야 한다.
- **FR-007**: 세션 테이블에는 UK 제약조건을 생성하지 않아야 한다.
- **FR-008**: 세션 테이블에는 별도의 추가 INDEX를 생성하지 않아야 한다.
- **FR-009**: 세션 토큰 원문은 데이터베이스에 저장하지 않고 검증 가능한 안전한 식별 정보로 저장해야 한다.
- **FR-010**: 인증 요청이 들어오면 시스템은 세션 존재 여부, 데이터 종료 여부, 만료 여부, 사용자 로그인 가능 여부를 확인해야 한다.
- **FR-011**: 만료된 세션은 인증에 성공할 수 없어야 한다.
- **FR-012**: 로그아웃 시 해당 세션은 폐기 상태로 기록되어야 하며 이후 인증에 사용할 수 없어야 한다.
- **FR-013**: 백엔드가 재기동되어도 만료되지 않고 폐기되지 않은 세션은 다시 인증에 사용할 수 있어야 한다.
- **FR-014**: 세션 기본 유효기간은 로그인 성공 시점부터 8시간으로 유지한다.
- **FR-015**: 세션 유효기간은 사용자의 요청마다 자동으로 연장하지 않는 절대 만료 방식으로 동작해야 한다.
- **FR-016**: 기존 브라우저 새로고침 동작을 유지하며, 새로고침 시 저장된 토큰으로 서버 세션을 검증한다.
- **FR-017**: 세션이 유효하지 않은 경우 브라우저에 남아 있는 인증 정보도 제거하고 로그인 화면으로 이동해야 한다.

## 3. 제외 범위

- 다중 서버 간 세션 공유를 위한 별도 캐시 시스템 도입은 제외한다.
- 세션 관리 화면, 운영자용 세션 강제 종료 화면은 제외한다.
- 로그인 방식 자체의 변경, 비밀번호 정책 변경, 권한 체계 변경은 제외한다.
- 기존 인증 API의 사용자 경험을 변경하지 않는다.

## 4. 사용자 시나리오 및 테스트

### 시나리오 1 - 로그인 후 백엔드 재기동

**우선순위**: P1

**Given** 유효한 계정으로 로그인하여 세션이 생성된 상태

**When** 백엔드를 재기동한 후 같은 브라우저로 페이지를 새로고침

**Then** 세션 만료 시각이 지나지 않았다면 로그인 화면으로 이동하지 않고 기존 화면에 진입해야 한다.

### 시나리오 2 - 세션 만료

**우선순위**: P1

**Given** 로그인 세션의 만료 시각이 지난 상태

**When** 보호된 기능을 요청하거나 페이지를 새로고침

**Then** 요청은 인증 실패로 처리되고 저장된 인증 정보는 제거되어야 한다.

### 시나리오 3 - 로그아웃한 세션 재사용 차단

**우선순위**: P1

**Given** 로그인 후 로그아웃하여 세션이 폐기된 상태

**When** 폐기 전 토큰으로 보호된 기능을 요청

**Then** 해당 요청은 인증 실패로 처리되어야 한다.

### 시나리오 4 - 기존 로그인 흐름 유지

**우선순위**: P2

**Given** 정상적인 사용자 계정과 잘못된 사용자 계정이 각각 존재하는 상태

**When** 로그인 시도

**Then** 정상 계정은 세션을 생성하고, 잘못된 계정은 세션을 생성하지 않아야 한다.

## 5. 경계 조건 및 오류 처리

- 존재하지 않는 토큰은 유효하지 않은 세션으로 처리한다.
- 빈 토큰은 세션 조회 없이 인증 실패로 처리한다.
- 만료된 세션은 사용자 정보가 존재하더라도 인증하지 않는다.
- 데이터 종료 처리된 세션은 만료 시각이 남아 있어도 인증하지 않는다.
- 세션이 연결된 사용자가 비활성, 퇴직 또는 데이터 종료 상태이면 인증하지 않는다.
- 데이터베이스에서 세션 조회에 실패하면 보호된 요청은 인증 실패로 처리하고 내부 오류를 외부에 노출하지 않는다.
- 같은 사용자가 여러 브라우저에서 로그인할 수 있으며, 새 로그인은 기존 세션을 자동 폐기하지 않는다.

## 6. 데이터 규칙

### 세션 테이블

테이블명은 `TB_M26_AUTH_SESSION`으로 고정한다.

Audit 컬럼은 기존 프로젝트 표준에 따라 다음 업무 컬럼보다 먼저 배치한다.

- `CREATED_OBJECT_TYPE`
- `CREATED_OBJECT_ID`
- `CREATED_PROGRAM_ID`
- `CREATED_TIMESTAMP`
- `LAST_UPDATED_OBJECT_TYPE`
- `LAST_UPDATED_OBJECT_ID`
- `LAST_UPDATED_PROGRAM_ID`
- `LAST_UPDATED_TIMESTAMP`
- `DATA_END_STATUS`
- `DATA_END_OBJECT_TYPE`
- `DATA_END_OBJECT_ID`
- `DATA_END_PROGRAM_ID`
- `DATA_END_TIMESTAMP`

업무 컬럼에는 세션 식별자, 사용자 식별자, 토큰 해시, 만료 시각, 최종 접근 시각, 폐기 시각, 비고를 포함한다.

사용자 식별자는 논리적 참조로만 관리한다. FK, UK, 별도 INDEX는 생성하지 않는다. 기존 프로젝트의 데이터 종료 정책을 사용하며, 세션 폐기는 물리 삭제보다 상태 기록을 우선한다.

## 7. 성공 기준

- **SC-001**: 유효기간 내 세션은 백엔드 재기동 후에도 100% 재검증되어야 한다.
- **SC-002**: 만료 또는 폐기된 세션은 보호된 요청에서 100% 거부되어야 한다.
- **SC-003**: 로그인, 새로고침, 로그아웃의 기존 사용자 흐름이 변경되지 않아야 한다.
- **SC-004**: 유효하지 않은 세션이 확인되면 브라우저의 인증 정보가 제거되고 로그인 화면으로 이동해야 한다.
- **SC-005**: 세션 데이터에는 원문 인증 토큰이 저장되지 않아야 한다.

## 8. 가정

- 세션 유효기간은 현재 정책인 8시간을 유지한다.
- 세션 만료는 로그인 시각을 기준으로 하는 절대 만료 방식이다.
- 현재 운영 환경은 단일 백엔드 인스턴스이며, 별도 세션 캐시 도입은 필요하지 않다.
- 데이터베이스 스키마 변경은 Flyway 마이그레이션으로 관리한다.
- 테이블 및 컬럼 명명, Audit 컬럼 순서, 논리적 참조 원칙은 기존 M26 테이블 규칙을 따른다.
