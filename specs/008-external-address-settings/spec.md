# 기능 명세서: 기타 주소 설정 현황

**기능 브랜치**: `008-external-address-settings`

**작성일**: 2026-08-17

**상태**: 초안

**변경 추적**: 문서 변경 이력은 Git 커밋 이력을 기준으로 한다.

**입력**: 왼쪽 사이드바 관리자 메뉴 순서에 따라 "기타 주소 설정 현황" 기능명세서 작성

> **기능 개요 - Agent 요약**
>
> 기타 주소 설정 현황은 관리자 권한 사용자가 Vision Monitor와 외부 시스템 연결에 필요한 주소 정보를 확인하고 관리하는 화면이다. 관리자는 VMS, 미디어 서버, 이벤트 연동, 제어 연동처럼 운영에 필요한 endpoint 정보를 목록으로 확인하고, 어떤 주소가 어떤 기능과 연결되는지 이해할 수 있어야 한다. MVP에서는 설정 현황 확인과 mock 기반 편집 흐름까지 정의하고, 실제 저장/검증 연동은 후속 범위로 둔다.

## 2. 기능 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 관리자 권한 사용자는 기타 주소 설정 현황 화면에 진입할 수 있어야 한다.
- **FR-002**: 관리자 권한이 없는 사용자는 해당 메뉴와 화면에 접근할 수 없어야 한다.
- **FR-003**: 시스템은 외부 연동 주소 목록을 표시해야 한다.
- **FR-004**: 시스템은 주소명, 주소 구분, 연결 대상, 사용 여부, 최근 확인 상태를 표시해야 한다.
- **FR-005**: 사용자는 주소 구분, 사용 여부, 상태 조건으로 목록을 필터링할 수 있어야 한다.
- **FR-006**: 사용자는 특정 주소 항목을 선택해 상세 정보를 확인할 수 있어야 한다.
- **FR-007**: 관리자는 주소 항목을 추가할 수 있어야 한다.
- **FR-008**: 관리자는 기존 주소 항목을 수정할 수 있어야 한다.
- **FR-009**: 관리자는 더 이상 사용하지 않는 주소 항목을 비활성화할 수 있어야 한다.
- **FR-010**: 시스템은 주소 입력값이 비어 있거나 명확히 잘못된 경우 저장을 막고 이유를 표시해야 한다.
- **FR-011**: 시스템은 주소 변경이 모니터링, 제어 연동, 모델 기능에 영향을 줄 수 있음을 사용자에게 알려야 한다.
- **FR-012**: 시스템은 삭제보다 비활성화를 우선 제공해야 한다.

## 3. 제외 범위 *(필수)*

- 실제 외부 주소 연결 테스트와 운영 반영은 제외한다.
- 실제 저장소 반영과 배포 환경 설정 변경은 제외한다.
- 민감 정보 암호화 정책 구현은 제외한다.
- 주소 변경에 따른 서비스 재시작 자동화는 제외한다.
- 주소 변경 승인 워크플로우는 제외한다.

## 4. UI/UX 요구사항

- **UX-001**: 목록은 주소명, 구분, 사용 여부, 상태를 빠르게 스캔할 수 있어야 한다.
- **UX-002**: 수정/비활성화 동작은 실수 방지를 위해 영향 범위가 명확히 표시되어야 한다.
- **UX-003**: 주소 입력 오류는 입력 필드 근처에서 이해할 수 있게 표시되어야 한다.
- **UX-004**: 활성 주소와 비활성 주소는 명확히 구분되어야 한다.
- **UX-005**: theme1, theme2, theme3에서 상태와 입력 텍스트가 읽을 수 있어야 한다.

## 6. 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 주소 현황 조회 (우선순위: P1)

관리자는 외부 연동 주소 현황을 목록으로 확인한다.

**관련 기능 요구사항**: FR-001, FR-002, FR-003, FR-004, FR-005

**이 우선순위의 이유**: 주소 관리의 시작점은 현재 등록된 주소와 사용 상태를 정확히 파악하는 것이다.

**독립 테스트**: 관리자에게 목록과 필터가 표시되고 비관리자는 접근할 수 없는지 확인한다.

**허용 시나리오**:

1. **Given** 관리자 권한 사용자가 로그인되어 있다, **When** 기타 주소 설정 현황 메뉴를 선택한다, **Then** 주소 목록이 표시된다.
2. **Given** 주소 목록이 표시되어 있다, **When** 사용자가 사용 여부 필터를 선택한다, **Then** 조건에 맞는 주소만 표시된다.

### 사용자 스토리 2 - 주소 추가와 수정 (우선순위: P2)

관리자는 새 외부 주소를 추가하거나 기존 주소 정보를 수정한다.

**관련 기능 요구사항**: FR-006, FR-007, FR-008, FR-010, FR-011

**이 우선순위의 이유**: 운영 중 외부 시스템 주소 변경이 발생할 수 있으므로 관리 흐름이 필요하다.

**독립 테스트**: 추가/수정 입력과 유효성 오류, 영향 안내가 표시되는지 확인한다.

**허용 시나리오**:

1. **Given** 주소 목록이 표시되어 있다, **When** 사용자가 주소 추가를 선택하고 필수 정보를 입력한다, **Then** 새 주소가 등록 가능한 상태로 표시된다.
2. **Given** 주소 수정 화면이 표시되어 있다, **When** 필수 주소값을 비운다, **Then** 저장이 막히고 오류가 표시된다.

### 사용자 스토리 3 - 주소 비활성화 (우선순위: P3)

관리자는 더 이상 사용하지 않는 주소를 비활성화한다.

**관련 기능 요구사항**: FR-009, FR-012

**이 우선순위의 이유**: 삭제보다 되돌릴 수 있는 비활성화가 운영 리스크를 줄인다.

**독립 테스트**: 비활성화 후 목록에서 상태가 바뀌고 삭제 동작이 기본 제공되지 않는지 확인한다.

**허용 시나리오**:

1. **Given** 활성 주소가 선택되어 있다, **When** 사용자가 비활성화를 실행한다, **Then** 주소 상태가 비활성으로 변경된다.

### 엣지 케이스

- 중복 주소명이 입력되면 사용자가 충돌을 이해할 수 있어야 한다.
- 비활성 주소는 기본 운영 주소로 오해되지 않아야 한다.
- 주소가 길어도 목록 레이아웃이 깨지지 않아야 한다.

## 7. 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 관리자는 2번 이하의 조작으로 주소 현황 화면에 진입할 수 있다.
- **SC-002**: 관리자는 3초 이내에 활성/비활성 주소 수를 파악할 수 있다.
- **SC-003**: 관리자는 3개 이하의 필터 조작으로 원하는 주소 구분을 찾을 수 있다.
- **SC-004**: 잘못된 주소 입력은 저장 전에 사용자에게 표시된다.
- **SC-005**: 비관리자는 메뉴와 화면 내용을 볼 수 없다.

## 8. 가정 및 미정 사항

### 가정

- MVP는 mock 데이터와 mock 저장 흐름으로 진행한다.
- 실제 운영 반영은 후속 기능에서 다룬다.

### 미정 사항

- 주소 구분의 최종 분류와 필수 입력 항목은 외부 시스템 계약 확정 후 조정한다.
